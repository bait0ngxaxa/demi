# WB Alignment Decision Register

Decision Register ที่บันทึกตามที่ Product Owner ส่งมา (WB = Whiteboard ของลูกค้า). Defaults `WB-DF-*` ถูกตัดสินใช้ไปก่อนและให้ลูกค้ายืนยันภายหลัง (ปรับได้ต้นทุนต่ำ); `WB-PD-*` รอ decision ก่อนทำ.

เอกสารนี้เป็น decision register ไม่ใช่ capability inventory — สถานะของแต่ละ capability อยู่ใน [BUSINESS_FLOW_GAP_CANONICAL.md](./BUSINESS_FLOW_GAP_CANONICAL.md).

## ค. การนำ Phase A ไปใช้ (WB-DF-01..05, WB-PD-01/10)

บันทึกการตัดสินใจเชิงออกแบบที่ทำเพื่อให้ defaults ข้างต้นทำงานได้ ซึ่งไม่ได้ระบุไว้ชัดใน register:

1. **เลขรอบ Follow-up (ข้อควรระวังเรื่องชื่อ).** `PatientFollowup.roundNumber` ของ Program เริ่มนับที่ 1 (ทั้งใน `followup-service` และใน workbook ที่ใช้ "Follow-up 1–4" ในคอลัมน์ครั้งที่ 3–6) ดังนั้น "ครั้งที่ 3–6" ใน WB-DF-01 หมายถึง Follow-up `roundNumber` 1–4 โดย `ครั้งที่ N = Follow-up N − 2`. ไม่ได้เปลี่ยนค่าที่เก็บอยู่ใน `PatientFollowup`. Follow-up ลำดับที่ 5 ขึ้นไปยังอยู่ใน workbook/ประวัติ Follow-up ตามเดิม แต่ไม่มีช่องในตัวนำทาง 1–6.
2. **Goal Plan ครั้งที่ 2.** Goal Plan แรกของ Program (`PatientGoalPlan.roundNumber = 1`) คือครั้งที่ 2. แผนที่ปรับภายหลัง (`sourceFollowupId`) ไม่ใช่ครั้งใหม่ แต่แสดงเป็นแผนที่ใช้ติดตามในครั้งนั้น.
3. **ครั้งที่ 1 และการบันทึกซ้ำ.** เครื่องมือ Service 1 และแบบประเมิน PAM/PROMs เป็นผลระดับ Program (หนึ่งผลต่อ Program) และถูกบันทึกเป็นกิจกรรมของครั้งที่ 1 ใน ledger ทันทีที่บันทึก. ในครั้งหลัง เครื่องมือเดียวกันทำได้เพียง "ทบทวน" (WB-DF-03) — ไม่มีการสร้างผลที่สองทับ. เครื่องมือที่ยังไม่มีผลจะลิงก์กลับไปบันทึกที่ Service 1 / แบบประเมิน (นับเป็นครั้งที่ 1).
4. **EXTRA vs PLANNED.** `source` ถูกกำหนดที่ server จากรายการแนะนำของครั้งนั้น (`ROUND_RECOMMENDED_TOOLS`) ไม่รับจาก client. การ "Add การจัดบริการเพิ่ม" ในครั้งนี้จึงเป็น EXTRA เมื่อเครื่องมือไม่อยู่ในรายการแนะนำของครั้งนั้น และมองเห็นในประวัติของครั้งนั้น.
5. **รายการแนะนำต่อครั้ง.** (แก้โดย A-01) ตั้งตามกล่องบน Canva Whiteboard `DAHSvdQ3gvU` (ข้อความอ่านได้ 2026-10-14) ไม่ใช่ตาม Workbook; crosswalk, ข้อที่ยังไม่ปิด และกฎข้อมูลเดิมอยู่ใน [WB_ROUND_ACTIVITY_CROSSWALK.md](./WB_ROUND_ACTIVITY_CROSSWALK.md). รายการอยู่ที่ตารางเดียวใน `src/modules/patient-program-rounds/domain/round-catalog.ts`; WB-PD-10 ปิดใน Phase D (§จ).
6. **HEALTHY_PLAN / HEALTH_PLAN_REVIEW.** HEALTHY_PLAN derive จาก Goal Plan (ครั้งที่ 2) ซึ่งมี `roundNumber` ของตัวเองอยู่แล้ว จึงไม่เขียนซ้ำใน ledger. HEALTH_PLAN_REVIEW ไม่ derive จาก Follow-up อีกต่อไป: เป็น DONE ได้เฉพาะเมื่อมีแถว ledger ของตัวเอง (ยังไม่มีเส้นทางเขียน — U-4) ส่วน Follow-up แสดงแยกเป็น "มีบันทึกการติดตามผล" ผ่าน `followupId`. ยังไม่ได้ยืนยันว่า Goal Plan = "แผนสุขภาพ" (P-16) ซึ่งไม่ถูกปิดโดยงานนี้. HEALTH_PLAN_REVIEW ไม่ถือว่า DONE จากการมี Follow-up อย่างเดียว (A-02) และรายการติดตามแสดงเป็น "กิจกรรมในแผน" ไม่ใช่ due-only (A-03); ดู U-4/U-7 ใน `WB_ROUND_ACTIVITY_CROSSWALK.md`. **Superseded โดย D4–D6 (§จ):** ครั้งที่ 2 = ทำแผนสุขภาพ (PLANNED), HEALTH_PLAN_REVIEW ครั้งที่ 3–6 derive จาก Follow-up และรายการติดตามเป็น due/met.
7. **สัญญาณชีพครั้งที่ 1–2.** เก็บใน `PatientProgramRoundVitals` แบบสร้างครั้งเดียวต่อครั้ง (ไม่มีการแก้ไขภายหลัง เช่นเดียวกับ Baseline/Follow-up). ส่วนสูงแก้ได้ตอนบันทึกครั้งที่ 1–2 เท่านั้น (WB-DF-05); ครั้งที่ 3–6 ใช้ค่าล่าสุดแสดงอย่างเดียวและสัญญาณชีพมาจาก Follow-up.
8. **BMI ใน report.** Before = น้ำหนัก Baseline ÷ ส่วนสูง Baseline; After = น้ำหนัก Final Assessment ÷ ส่วนสูงล่าสุดที่บันทึก (ครั้งที่ 2 → ครั้งที่ 1 → Baseline) เพราะ Final Assessment ไม่มีส่วนสูงของตัวเอง. แสดงค่าเท่านั้น.
9. **PAM/PROMs ใน report.** มาจากแบบประเมินที่ผูกกับ Program (ทำจากครั้งที่ 1) เท่านั้น. แบบประเมินที่บันทึกนอก Program ยังไม่ผูกกับช่วงของ Program และไม่ถูกรายงาน.

1. **E1 สถานะความสัมพันธ์:** สิทธิ์มีผลเฉพาะเมื่อ membership ACTIVE; ระงับ/สิ้นสุดแล้วส่งออกไม่ได้ทันที (คำขอถัดไป). ค่าที่บันทึกไว้ไม่ถูกล้างเมื่อระงับ จึงกลับมามีผลเมื่อคืนสถานะ ACTIVE; หากไม่ต้องการ OWNER ต้องยกเลิกสิทธิ์เอง (สถานะสิทธิ์แสดงในหน้ารายละเอียดบุคลากร). การเลื่อนเป็น OWNER ล้างสิทธิ์ (OWNER ส่งออกได้ตามบทบาท). MEMBER ที่ไม่มีสิทธิ์ยังเปิดหน้ารายงาน/dashboard ไม่ได้ (404 เดิม); เฉพาะการส่งออกที่ตอบ 403.
2. **E2 QR ของคำเชิญที่มีอยู่:** ระบบเก็บเฉพาะ hash ของ token (Phase 17F.3) จึงสร้างลิงก์เดิมซ้ำไม่ได้. การกด “แสดงคิวอาร์โค้ด” จึงหมุน secret ของคำเชิญเดิม: ผู้รับ วันหมดอายุ และกฎการตอบรับเหมือนเดิม ลิงก์/QR ก่อนหน้าใช้ไม่ได้ทันที; audit `caregiver_invitation.link_reissued` (ไม่มี token). ส่งผ่าน Server Action ซึ่ง Next.js ตอบด้วย `Cache-Control: no-cache, no-store`; plaintext ไม่ถูกเก็บ. ตอบรับผ่าน QR = ตอบรับผ่านลิงก์ (URL เดียวกัน). แทนที่ข้อกำหนด “ไม่มี show-QR-again” ของ Phase 17F.3 เฉพาะคำเชิญ PENDING.
3. **E3 “ผูก รพ. เดียว”:** นับทุกความสัมพันธ์ของ Person — ความสัมพันธ์ผู้ป่วย และความสัมพันธ์บุคลากร/อสม. ที่ยังไม่ ENDED — เพราะชื่อเป็นของ Person ที่ใช้ร่วมกัน (fail closed). Audit ไม่เก็บชื่อเก่า/ใหม่ (ตามแนวเดิม: ไม่มี audit ใดเก็บชื่อบุคคล) แต่บันทึกว่าแก้ชื่อ/นามสกุลส่วนใด พร้อมเวอร์ชันและฐานสิทธิ์. การเติมชื่อที่ว่างตอนลงทะเบียนผู้ป่วยก็เพิ่ม `Person.version`.
4. **E4 เบอร์ผู้ป่วย:** ใช้กฎโปรไฟล์ที่มีผล (โปรไฟล์ระดับ รพ. ถ้ามี มิฉะนั้นโปรไฟล์กลาง) เช่นเดียวกับหน้าข้อมูลผู้ป่วย. ผู้ป่วยไม่เห็นเบอร์ของตนในรายละเอียดนัด. เบอร์ รพ. เป็นข้อมูลติดต่อของ รพ. ไม่ใช่ข้อมูลผู้ป่วย จึงไม่เปลี่ยน `family-appointment-read-v1`.
5. **E5 ช่วงค่า/เวลา:** ช่วงค่าเท่ากับ `PatientFollowup` (0–1,000,000, ไม่บังคับหน่วย) และต้องมีอย่างน้อยหนึ่งค่า; เวลาวัดต้องไม่เป็นอนาคตเกิน 5 นาทีและไม่เก่ากว่า 366 วัน. ลบได้ภายใน 24 ชั่วโมงหลังบันทึก (soft delete + audit) หลังจากนั้นแก้/ลบไม่ได้. ไม่มีการตรวจรับรองโดยเจ้าหน้าที่. อสม. ต้องได้รับมอบหมายปัจจุบัน; เจ้าหน้าที่ต้องเป็นของ รพ. ของความสัมพันธ์นั้น (บันทึกเป็นของ PatientProfile จึงเห็นได้ทุก รพ. ที่ผู้ป่วยผูก).
6. **E6 เวลาที่กำหนดผู้รับ:** ผู้รับถูกกำหนดตอนเกิดเหตุการณ์ (source) แล้วตรวจซ้ำตอนส่ง: อสม. ต้องยังเป็นผู้ได้รับมอบหมายปัจจุบัน และ grant ต้องยัง ACTIVE; อสม. ที่ได้รับมอบหมายหลังเหตุการณ์ไม่ได้รับข้อความของเหตุการณ์นั้น. ญาติได้รับเฉพาะเมื่อเปิด `FAMILY_DELEGATED_APPOINTMENT_READ_ENABLED`. ผู้ใช้คนเดียวที่มีหลายบทบาทได้ข้อความเดียวต่อเหตุการณ์. ข้อความเดิม (ไม่มีรายละเอียดทางคลินิก). การเปิดรับแจ้งเตือนอยู่ที่หน้าบัญชี LINE สำหรับ อสม./ญาติ (หน้าตั้งค่ายังแสดงเฉพาะผู้ป่วย).

ไม่อยู่ในขอบเขต: ญาติดูยา/แผนสุขภาพ (ก-16, รอ ก-25 / WB-PD-07), การสิ้นสุดการดูแล (Phase F), เขตความรับผิดชอบ (Phase G), ข้อความ PDPA (WB-PD-06).

การตีความที่ใช้ตอนนำไปใช้:

1. **ตัวเลือกเขตงาน (STAFF-04):** หน้าพื้นที่ทำงานแสดง “เขตความรับผิดชอบ” จัดตามเครือข่าย สร้างจาก membership โดยตรงที่ ACTIVE (บทบาท HOSPITAL) และความสัมพันธ์ อสม. ที่ ACTIVE (บทบาท OSM) ที่ รพ. ACTIVE เท่านั้น; สมาชิกแม่ข่ายไม่เห็นลูกข่ายเป็นบริบทงาน; ผู้ใช้ รพ. เดียวไม่เห็นตัวเลือก (เหมือนเดิม). ชื่อเครือข่ายเป็นป้ายกำกับเท่านั้น ไม่ให้สิทธิ์.
2. **ภาพรวมเขต (`/app/hospitals/areas`):** เฉพาะ OWNER ของแม่ข่ายที่มีลูกข่าย ACTIVE; แต่ละลูกข่ายอ่านผ่านเส้นทางรายงานลูกข่ายเดิม (ตรวจสิทธิ์และ audit `parent_child_reporting.access.read` ทีละแห่ง); ลูกข่ายที่ไม่ผ่านการตรวจซ้ำถูกตัดออก.
3. **ไฟล์ RPT-32:** ชีตเดียว “สรุปรายลูกข่าย” = ชื่อแม่ข่าย/ลูกข่าย เวลาที่สร้างไฟล์ (เวลาไทย), ชุดข้อมูล (ไม่รวมผู้ที่สิ้นสุดการดูแล) และ 9 ค่า; ไม่มี ID, รหัสโรงพยาบาล, HN, ชื่อ, ช่องทางติดต่อ หรือค่าวัด; ไม่ใช้ template ของ OWNER (ซึ่งเป็นแถวรายผู้ป่วย) และไม่ใช้ `reportExportGrantedAt`. audit `parent_child_reporting.export.prepared|denied|failed` (ผู้ทำ แม่ข่าย ลูกข่าย ผลและเหตุผล เวลาจากฐานข้อมูล; ไม่เก็บตัวเลข); ถ้าบันทึก audit ไม่ได้จะไม่ส่งไฟล์. Contract: unauthenticated request ตอบ 401 และไม่สร้าง audit; หลังยืนยัน session แต่ถูกปฏิเสธก่อนมี ActorContext บันทึก actorless `denied` โดยไม่เก็บ locator; authenticated request ที่มี ActorContext ใช้ event เดียวต่อ outcome และ route ไม่เขียนซ้ำ.
4. **ไม่อยู่ในขอบเขต / real-data gate:** UI เพิ่ม/ถอดลูกข่าย, ประวัติ hierarchy แบบ effective-dated, การส่งออกรายผู้ป่วยตามเขต, transfer workflow, cell suppression และการเปลี่ยนสิทธิ์ workforce ของลูกข่ายยังไม่อนุมัติ. H5 กำหนด current authorization เท่านั้น ไม่ได้ตัดสินการเปิดเผย aggregate ที่ source records อาจเกิดก่อน current Parent link หรือ safeguard สำหรับจำนวนต่ำ; คง aggregate-only demonstration ด้วย synthetic fixtures ใน controlled test database และรอคำถาม Owner ใน [Reporting Access Canonical](./REPORTING_ACCESS_CANONICAL.md) §5 ก่อนใช้ real data กับหน้า view หรือ export. ไม่มี runtime mode แยก synthetic/real และไม่มีการสมมติ threshold, consent หรือ effective date.
