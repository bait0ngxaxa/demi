# WB Alignment Decision Register

Decision Register ที่บันทึกตามที่ Product Owner ส่งมา (WB = Whiteboard ของลูกค้า). Defaults `WB-DF-*` ถูกตัดสินใช้ไปก่อนและให้ลูกค้ายืนยันภายหลัง (ปรับได้ต้นทุนต่ำ); `WB-PD-*` รอ decision ก่อนทำ.

เอกสารนี้เป็น decision register ไม่ใช่ capability inventory — สถานะของแต่ละ capability อยู่ใน [BUSINESS_FLOW_GAP_CANONICAL.md](./BUSINESS_FLOW_GAP_CANONICAL.md).

## ค. การนำ Phase A ไปใช้ (WB-DF-01..05, WB-PD-01/10)

บันทึกการตัดสินใจเชิงออกแบบที่ทำเพื่อให้ defaults ข้างต้นทำงานได้ ซึ่งไม่ได้ระบุไว้ชัดใน register:

1. **เลขรอบ Follow-up (ข้อควรระวังเรื่องชื่อ).** `PatientFollowup.roundNumber` ของ Program เริ่มนับที่ 1 (ทั้งใน `followup-service` และใน workbook ที่ใช้ "Follow-up 1–4" ในคอลัมน์ครั้งที่ 3–6) ดังนั้น "ครั้งที่ 3–6" ใน WB-DF-01 หมายถึง Follow-up `roundNumber` 1–4 โดย `ครั้งที่ N = Follow-up N − 2`. ไม่ได้เปลี่ยนค่าที่เก็บอยู่ใน `PatientFollowup`. Follow-up ลำดับที่ 5 ขึ้นไปยังอยู่ใน workbook/ประวัติ Follow-up ตามเดิม แต่ไม่มีช่องในตัวนำทาง 1–6.
2. **Goal Plan ครั้งที่ 2.** Goal Plan แรกของ Program (`PatientGoalPlan.roundNumber = 1`) คือครั้งที่ 2. แผนที่ปรับภายหลัง (`sourceFollowupId`) ไม่ใช่ครั้งใหม่ แต่แสดงเป็นแผนที่ใช้ติดตามในครั้งนั้น.
3. **ครั้งที่ 1 และการบันทึกซ้ำ.** เครื่องมือ Service 1 และแบบประเมิน PAM/PROMs เป็นผลระดับ Program (หนึ่งผลต่อ Program) และถูกบันทึกเป็นกิจกรรมของครั้งที่ 1 ใน ledger ทันทีที่บันทึก. ในครั้งหลัง เครื่องมือเดียวกันทำได้เพียง "ทบทวน" (WB-DF-03) — ไม่มีการสร้างผลที่สองทับ. เครื่องมือที่ยังไม่มีผลจะลิงก์กลับไปบันทึกที่ Service 1 / แบบประเมิน (นับเป็นครั้งที่ 1).
4. **EXTRA vs PLANNED.** `source` ถูกกำหนดที่ server จากรายการแนะนำของครั้งนั้น (`ROUND_RECOMMENDED_TOOLS`) ไม่รับจาก client. การ "Add การจัดบริการเพิ่ม" ในครั้งนี้จึงเป็น EXTRA เมื่อเครื่องมือไม่อยู่ในรายการแนะนำของครั้งนั้น และมองเห็นในประวัติของครั้งนั้น.
5. **รายการแนะนำต่อครั้ง.** (แก้โดย A-01) ตั้งตามกล่องบน Canva Whiteboard `DAHSvdQ3gvU` (ข้อความอ่านได้ 2026-10-14) ไม่ใช่ตาม Workbook; crosswalk, ข้อที่ยังไม่ปิด และกฎข้อมูลเดิมอยู่ใน [WB_ROUND_ACTIVITY_CROSSWALK.md](./WB_ROUND_ACTIVITY_CROSSWALK.md). รายการอยู่ที่ตารางเดียวใน `src/modules/patient-program-rounds/domain/round-catalog.ts`; WB-PD-10 ยังไม่ปิด.
6. **HEALTHY_PLAN / HEALTH_PLAN_REVIEW.** ทั้งสองถูก derive จาก Goal Plan (ครั้งที่ 2) และ Follow-up (ครั้งที่ 3–6) ซึ่งมี `roundNumber` ของตัวเองอยู่แล้ว จึงไม่เขียนซ้ำใน ledger. ยังไม่ได้ยืนยันว่า Goal Plan = "แผนสุขภาพ" (P-16) ซึ่งไม่ถูกปิดโดยงานนี้.
7. **สัญญาณชีพครั้งที่ 1–2.** เก็บใน `PatientProgramRoundVitals` แบบสร้างครั้งเดียวต่อครั้ง (ไม่มีการแก้ไขภายหลัง เช่นเดียวกับ Baseline/Follow-up). ส่วนสูงแก้ได้ตอนบันทึกครั้งที่ 1–2 เท่านั้น (WB-DF-05); ครั้งที่ 3–6 ใช้ค่าล่าสุดแสดงอย่างเดียวและสัญญาณชีพมาจาก Follow-up.
8. **BMI ใน report.** Before = น้ำหนัก Baseline ÷ ส่วนสูง Baseline; After = น้ำหนัก Final Assessment ÷ ส่วนสูงล่าสุดที่บันทึก (ครั้งที่ 2 → ครั้งที่ 1 → Baseline) เพราะ Final Assessment ไม่มีส่วนสูงของตัวเอง. แสดงค่าเท่านั้น.
9. **PAM/PROMs ใน report.** มาจากแบบประเมินที่ผูกกับ Program (ทำจากครั้งที่ 1) เท่านั้น. แบบประเมินที่บันทึกนอก Program ยังไม่ผูกกับช่วงของ Program และไม่ถูกรายงาน.

## ง. การนำ Phase B ไปใช้ (WB-DF-06..11)

- **คำขอเลื่อนนัด:** ช่วงเสนอวันเวลา = อนาคตไม่เกิน 366 วัน ณ เวลาส่ง (เวลาประเทศไทย), 1–3 ตัวเลือกไม่ซ้ำ, เหตุผลต้องระบุ ≤500 ตัวอักษร. เก็บ source, nonce, เวอร์ชันนัดขณะส่ง และผู้/เวลาพิจารณาแยกจากตัวนัด. ไม่สร้างสถานะอนุมัติระหว่างนำทาง: จะ APPROVED เมื่อเจ้าหน้าที่แก้วันเวลาสำเร็จใน transaction เดียวเท่านั้น. การแก้นัดอื่นหรือเปลี่ยนเป็น terminal จะ SUPERSEDED คำขอค้าง. อสม. พิจารณาคำขอแทนโรงพยาบาลไม่ได้.
- **ผู้อ่านประวัติคำขอ:** Product Owner ยืนยันใน Phase B ให้เฉพาะผู้ป่วย SELF, อสม. ที่ยังได้รับมอบหมาย และเจ้าหน้าที่โรงพยาบาลที่มีสิทธิ์ตรงกัน. คง `family-appointment-read-v1` เดิม: ญาติไม่เห็นเหตุผลหรือประวัติการดำเนินการของคำขอ.
- **นัดเยี่ยมบ้าน / ชุมชน:** ใช้ `HOME_VISIT` เดิม; อสม. ต้องยังได้รับมอบหมาย และแก้/ยกเลิกได้เฉพาะที่ตนสร้าง. ห้ามระบุผู้รับผิดชอบคลินิก เปลี่ยนเป็นสถานที่คลินิก หรือ complete/no-show. นัดคลินิกและตัวเลือกแพทย์/พยาบาลคงขอบเขตเดิม.
- **นำออกจากระบบ:** `MembershipStatus.ENDED` เป็น terminal ของ relationship ไม่ใช่ลบ Person/User หรือปิดบทบาทอื่น/โรงพยาบาลอื่น. เปลี่ยน namespace uniqueness เป็นหนึ่ง relationship ที่ยังไม่ ENDED ต่อคน/โรงพยาบาล; provisioning สร้างรายการใหม่และคง ENDED เดิม. การนำออกปิด assignment ของบุคคลในโรงพยาบาลนี้ และเพิกถอน workforce activation/reset ที่ค้างทุกใบของบุคคล เพราะเป็น credential capability ระดับบัญชี. ระงับ/คืนสิทธิ์ยังรองรับ ACTIVE/SUSPENDED เดิม; DB trigger ป้องกันคืน ENDED.
- **โปรไฟล์:** OWNER และ MEMBER ที่ ACTIVE ของโรงพยาบาลตรงกันเท่านั้นแก้ hospital-local fields ได้; expectedVersion = 0 สำหรับข้อมูล fallback ที่ยังไม่มี local record. strict schema ปฏิเสธชื่อ-สกุล/Person identity; WB-PD-09 ไม่ถูกปิด.
- **ประวัติสุขภาพ:** แยกตาม PatientHospitalRelationship, optimistic concurrency เช่นโปรไฟล์. มี/ไม่มี/ไม่ทราบเป็นข้อมูลที่เจ้าหน้าที่บันทึก ไม่อนุมานจาก PatientClassification. ญาติสายตรงหมายถึงบิดา มารดา พี่น้อง หรือบุตร; โรคอื่นเป็นข้อความ ≤1,000 ตัวอักษร. ปีวินิจฉัยเป็น พ.ศ. ตั้งแต่ 2400 ถึงปีปัจจุบันประเทศไทย หรือไม่ทราบ (null).
- **ระยะเวลาในรายงาน:** ปี พ.ศ. ปัจจุบันประเทศไทย − diagnosisYear (จำนวนปีเต็มตามปีปฏิทิน; ปีเดียวกัน = 0); ไม่ทราบปีจะแสดง “ไม่ทราบปีวินิจฉัย”. ใช้ประวัติระดับโรงพยาบาลปัจจุบัน จึงไม่ใช่ snapshot ณ วันเริ่ม Program และไม่ใช่ระยะเวลาตั้งแต่เริ่ม Program. ค่าใน Dashboard และคอลัมน์ E ของทั้งสอง sheet มาจาก source เดียวกัน. ข้อนี้ supersedes CL-05/P-07 เฉพาะ default WB-DF-11; clinical metrics อื่นยัง pending.
