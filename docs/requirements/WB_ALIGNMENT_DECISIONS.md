# WB Alignment Decision Register

Decision Register ที่บันทึกตามที่ Product Owner ส่งมา (WB = Whiteboard ของลูกค้า). Defaults `WB-DF-*` ถูกตัดสินใช้ไปก่อนและให้ลูกค้ายืนยันภายหลัง (ปรับได้ต้นทุนต่ำ); `WB-PD-*` รอ decision ก่อนทำ.

เอกสารนี้เป็น decision register ไม่ใช่ capability inventory — สถานะของแต่ละ capability อยู่ใน [BUSINESS_FLOW_GAP_CANONICAL.md](./BUSINESS_FLOW_GAP_CANONICAL.md).

## SR-1. การลงทะเบียนเองด้วยเลขบัตร (Product Owner, 2026-10-22)

คำตัดสินนี้บันทึกใน [ADR-0020](../adr/0020-self-registration-by-national-id.md) และยอมรับความเสี่ยงโดยตรงว่าเลขบัตรไม่ใช่หลักฐานความเป็นเจ้าของบัญชี

| Decision | ข้อกำหนดที่นำไปใช้ |
| --- | --- |
| SR-D1 — Eligibility | ตรวจที่ lookup และ completion: User ยัง PROVISIONED และไม่เคยมี credential, ไม่มี claim/quarantine ค้าง, ไม่มี OWNER membership หรือ ADMIN, และมี relationship PROVISIONED ที่เข้าเกณฑ์ (MEMBER/OSM/Patient ที่ยังไม่สิ้นสุด) ใน Hospital ACTIVE ที่เปิด switch และ record อายุไม่เกิน 30 วัน; ทุกกรณีที่ไม่เข้าเกณฑ์ตอบ NOT_FOUND เหมือนกัน |
| SR-D2 — Hospital setting | switch “อนุญาตให้ลงทะเบียนเองด้วยเลขบัตร” ค่าเริ่มต้นเปิด; แก้ได้เฉพาะ OWNER โดยมี audit; ปิดแล้วมีผลทันที |

## ค. การนำ Phase A ไปใช้ (WB-DF-01..05, WB-PD-01/10)

1. **เลขรอบ Follow-up (ข้อควรระวังเรื่องชื่อ).** `PatientFollowup.roundNumber` ของ Program เริ่มนับที่ 1 (ทั้งใน `followup-service` และใน workbook ที่ใช้ "Follow-up 1–4" ในคอลัมน์ครั้งที่ 3–6) ดังนั้น "ครั้งที่ 3–6" ใน WB-DF-01 หมายถึง Follow-up `roundNumber` 1–4 โดย `ครั้งที่ N = Follow-up N − 2`. ไม่ได้เปลี่ยนค่าที่เก็บอยู่ใน `PatientFollowup`. Follow-up ลำดับที่ 5 ขึ้นไปยังอยู่ใน workbook/ประวัติ Follow-up ตามเดิม แต่ไม่มีช่องในตัวนำทาง 1–6.
2. **Goal Plan ครั้งที่ 2.** Goal Plan แรกของ Program (`PatientGoalPlan.roundNumber = 1`) คือครั้งที่ 2. แผนที่ปรับภายหลัง (`sourceFollowupId`) ไม่ใช่ครั้งใหม่ แต่แสดงเป็นแผนที่ใช้ติดตามในครั้งนั้น.
3. **ครั้งที่ 1 และการบันทึกซ้ำ.** เครื่องมือ Service 1 และแบบประเมิน PAM/PROMs เป็นผลระดับ Program (หนึ่งผลต่อ Program) และถูกบันทึกเป็นกิจกรรมของครั้งที่ 1 ใน ledger ทันทีที่บันทึก. ในครั้งหลัง เครื่องมือเดียวกันทำได้เพียง "ทบทวน" (WB-DF-03) — ไม่มีการสร้างผลที่สองทับ. เครื่องมือที่ยังไม่มีผลจะลิงก์กลับไปบันทึกที่ Service 1 / แบบประเมิน (นับเป็นครั้งที่ 1).
4. **EXTRA vs PLANNED.** `source` ถูกกำหนดที่ server จากรายการแนะนำของครั้งนั้น (`ROUND_RECOMMENDED_TOOLS`) ไม่รับจาก client. การ "Add การจัดบริการเพิ่ม" ในครั้งนี้จึงเป็น EXTRA เมื่อเครื่องมือไม่อยู่ในรายการแนะนำของครั้งนั้น และมองเห็นในประวัติของครั้งนั้น.
5. **รายการแนะนำต่อครั้ง.** (แก้โดย A-01) ตั้งตามกล่องบน Canva Whiteboard `DAHSvdQ3gvU` (ข้อความอ่านได้ 2026-10-14) ไม่ใช่ตาม Workbook; crosswalk, ข้อที่ยังไม่ปิด และกฎข้อมูลเดิมอยู่ใน [WB_ROUND_ACTIVITY_CROSSWALK.md](./WB_ROUND_ACTIVITY_CROSSWALK.md). รายการอยู่ที่ตารางเดียวใน `src/modules/patient-program-rounds/domain/round-catalog.ts`; WB-PD-10 ปิดใน Phase D (§จ).

HEALTH_PLAN_REVIEW ไม่ derive จาก Follow-up อีกต่อไป: เป็น DONE ได้เฉพาะเมื่อมีแถว ledger ของตัวเอง (ยังไม่มีเส้นทางเขียน — U-4) ส่วน Follow-up แสดงแยกเป็น "มีบันทึกการติดตามผล" ผ่าน `followupId`. ยังไม่ได้ยืนยันว่า Goal Plan = "แผนสุขภาพ" (P-16) ซึ่งไม่ถูกปิดโดยงานนี้. HEALTH_PLAN_REVIEW ไม่ถือว่า DONE จากการมี Follow-up อย่างเดียว (A-02) และรายการติดตามแสดงเป็น "กิจกรรมในแผน" ไม่ใช่ due-only (A-03); ดู U-4/U-7 ใน `WB_ROUND_ACTIVITY_CROSSWALK.md`. **Superseded โดย D4–D6 (§จ):** ครั้งที่ 2 = ทำแผนสุขภาพ (PLANNED), HEALTH_PLAN_REVIEW ครั้งที่ 3–6 derive จาก Follow-up และรายการติดตามเป็น due/met.

## ง. การนำ Phase B ไปใช้ (WB-DF-06..11)

- **คำขอเลื่อนนัด:** ช่วงเสนอวันเวลา = อนาคตไม่เกิน 366 วัน ณ เวลาส่ง (เวลาประเทศไทย), 1–3 ตัวเลือกไม่ซ้ำ, เหตุผลต้องระบุ ≤500 ตัวอักษร. เก็บ source, nonce, เวอร์ชันนัดขณะส่ง และผู้/เวลาพิจารณาแยกจากตัวนัด. ไม่สร้างสถานะอนุมัติระหว่างนำทาง: จะ APPROVED เมื่อเจ้าหน้าที่แก้วันเวลาสำเร็จใน transaction เดียวเท่านั้น. การแก้นัดอื่นหรือเปลี่ยนเป็น terminal จะ SUPERSEDED คำขอค้าง. อสม. พิจารณาคำขอแทนโรงพยาบาลไม่ได้.
- **วันเวลาที่อนุมัติ (B-01 — ปิดโดย ก-23 ใน Phase D: ลูกค้ายืนยันตัวเลือก 1 "คงเดิม"; ข้อความด้านล่างเก็บไว้เป็นประวัติ):** WB-DF-06 ระบุเพียง "อนุมัติ (แก้นัดด้วย flow แก้ไขเดิม)" และ Canva Whiteboard `DAHSvdQ3gvU` มีเพียง "Popup กดยืนยัน/เลื่อนนัด" และ "กรณีขอเลื่อนนัด" โดยไม่มีกฎการเลือกวันเวลา. พฤติกรรมปัจจุบันจึงคงไว้ตามที่ทำไปแล้ว: ฟอร์มแก้นัดเติมตัวเลือกแรกให้และแสดงทุกตัวเลือก แต่ server ไม่บังคับว่าต้องตรงตัวเลือก. คำขอเป็น APPROVED เมื่อเจ้าหน้าที่โรงพยาบาลบันทึกวันเวลาที่ต่างจากเดิมสำเร็จ — แม้จะไม่ตรงกับตัวเลือกที่เสนอ. ถ้าไม่ได้เปลี่ยนวันเวลา, คำขอเป็นของนัดอื่น, คำขอไม่อยู่ใน PENDING หรือเวอร์ชันนัดไม่ตรง ทั้งการแก้นัดและการอนุมัติจะ rollback. การรับทราบนัดแยกจากคำขอและผูกกับเวอร์ชันนัด จึงต้องรับทราบใหม่หลังเลื่อน. ทางเลือกสำหรับ Product Owner:
  1. **คงเดิม — เลือกเวลาใดก็ได้:** ยืดหยุ่นตามตารางโรงพยาบาลและไม่ต้องส่งคำขอใหม่ แต่ผู้ป่วยจะเห็น "อนุมัติและแก้นัดแล้ว" แม้เวลาไม่ตรงกับที่ขอ (เวลาจริงแสดงในรายละเอียดนัด) และ audit ไม่ได้บันทึกว่าตรงตัวเลือกหรือไม่.
  2. **ต้องตรง 1 ตัวเลือก:** ความหมายของ "อนุมัติ" ชัดเจน แต่ถ้าทุกตัวเลือกไม่ว่าง เจ้าหน้าที่ต้องปฏิเสธแล้วให้ผู้ป่วยส่งคำขอใหม่ (เพิ่มรอบไป-กลับ); ต้องเพิ่ม validation ฝั่ง server และตัวเลือกใน UI แทนช่องกรอกอิสระ.
  3. **เลือกเวลาอื่นได้ แต่แยกผลลัพธ์จาก "อนุมัติ":** สื่อสารตรงกับผู้ป่วยที่สุด แต่ต้องมีผลลัพธ์/ข้อความสถานะใหม่ จึงต้องมี requirement ก่อน — ไม่สร้างสถานะใหม่จนกว่าจะได้รับการยืนยัน.

การตีความที่ใช้ตอนนำไปใช้:

1. **ธุรกรรมเดียว:** ตั้งค่าสิ้นสุด, ปิดการมอบหมาย อสม. ปัจจุบัน, ยกเลิกนัดที่ยัง SCHEDULED และยังไม่ถึงเวลา (สถานะ CANCELLED + audit `appointment.cancelled` ต่อรายการ เหมือนการยกเลิกปกติ แต่ไม่สร้างข้อความ LINE), คำขอเลื่อน/ยกเลิกนัดที่ค้าง → SUPERSEDED, คำขอรับบริการ PENDING/APPROVED → REJECTED (โดย OWNER), การเปิดใช้งานบัญชีของ รพ. นี้ที่ยังไม่ถูก claim → revoked, audit `patient.hospital_relationship.ended` (จำนวนที่ปิดแต่ละชนิด ไม่เก็บข้อความเหตุผล). นัดที่ผ่านมาแล้วคงสถานะเดิม. Program ที่ยัง ACTIVE ไม่ถูกปิดอัตโนมัติ (ไม่อยู่ในขอบเขต ก-18).
2. **เจ้าหน้าที่/อสม.:** อ่านหรือเขียนผู้ป่วยรายนี้ผ่าน รพ. นี้ไม่ได้ในทุก module (ไม่พบ = 404 เดิม) รวมรายชื่อผู้ป่วย, มอบหมาย อสม. (เดี่ยว/หลายราย), นัด, โปรแกรม/รอบ, ติดตาม, แผน, คัดกรอง, Baseline, หลักฐาน, จัดกลุ่ม, โปรไฟล์/ประวัติสุขภาพ, ค้นหาเพื่อเปิดใช้งานบัญชี และการแก้ชื่อ (OWNER; เส้นทาง ADMIN คงเดิม). การนับ “ผูก รพ. เดียว” ของ E3 ไม่นับความสัมพันธ์ผู้ป่วยที่สิ้นสุดแล้ว (เช่นเดียวกับ staff/OSM ที่ ENDED).
3. **ญาติ (เลือกแนวทาง “ไม่แตะ grant, fail closed”):** DB CHECK ของ `CaregiverAppointmentGrant` ให้ REVOKED ได้เฉพาะโดยผู้ป่วยที่เสนอ จึงไม่ revoke grant ในธุรกรรม; `appointmentGrantCaregiverWhere` ต้องการความสัมพันธ์ที่ยังไม่สิ้นสุด ญาติจึงไม่เห็นนัด ไม่ได้รับ LINE และตอบรับ grant ค้างไม่ได้. หน้าครอบครัวของผู้ป่วยแสดง grant นั้นว่า “สิ้นสุดการดูแลแล้ว” (ยังยกเลิกเองได้) และไม่ให้เลือก รพ. นั้นสำหรับ grant ใหม่.
4. **ผู้ป่วย (เลือก “ประวัติการดูแลเท่านั้น”):** รายการ รพ. ยังแสดงพร้อมป้าย “สิ้นสุดการดูแลแล้ว”; อ่านนัด โปรแกรม/รอบ ติดตาม แผน คัดกรอง Baseline ประวัติสุขภาพ และประวัติคำขอรับบริการได้อย่างเดียว; รับทราบ/ขอเลื่อน/ขอยกเลิกนัด ส่งคำขอรับบริการ แก้ข้อมูลสำหรับ รพ. นั้น และส่งเรื่องแจ้งปัญหาถึง รพ. นั้นไม่ได้; ไม่แสดงความรู้ ข้อมูลติดต่อ และเบอร์ รพ. ในรายละเอียดนัดของ รพ. นั้น. ผู้ป่วยที่ไม่มีความสัมพันธ์ที่ยังดูแลอยู่เลยไม่เปิดรับแจ้งเตือนนัดทาง LINE ได้. ยาและบันทึกส่วนตัว (รวมการเตือนยา) เป็นของบัญชีผู้ป่วย จึงไม่เปลี่ยน.
5. **LINE (เลือก “ไม่ส่ง”):** ธุรกรรมไม่สร้างข้อความยกเลิกนัด; ข้อความที่ค้างอยู่ถูกตัดตอนส่ง (`AUTHORITY_CHANGED`) เพราะการตรวจซ้ำตอนส่งต้องการความสัมพันธ์ที่ยังไม่สิ้นสุด.
6. **รายงาน:** cohort เริ่มต้น (`ACTIVE`) ไม่นับความสัมพันธ์ที่สิ้นสุดทั้งจำนวนผู้ป่วยและ Program; OWNER เลือก “รวมผู้ที่สิ้นสุดการดูแล” (`cohort=INCLUDE_ENDED`) ได้ที่หน้ารายงานและการส่งออก Excel ใช้ชุดเดียวกัน (มีหมายเหตุในไฟล์และ `cohort` ใน audit การส่งออก). cohort ไม่ถูกผูกใน cursor ที่ลงนาม (เป็นตัวกรอง ไม่ใช่มิติสิทธิ์; การผูก actor/รพ./page size/operation คงเดิม และ cursor เดิมยาวใกล้เพดาน 512). รายงานแม่ข่าย-ลูกข่าย, ADMIN และ MEMBER ที่ได้สิทธิ์ส่งออกใช้ cohort เริ่มต้น. รายงานราย Program ของผู้ป่วยปิดตามสิทธิ์ผู้ป่วย.
7. **การรับกลับ (เลือก “คง unique, ปฏิเสธ”):** unique `(patientProfileId, hospitalId)` คงเดิม ความสัมพันธ์ที่สิ้นสุดไม่ถูกเปิดกลับ. การเพิ่มผู้ป่วย (ฟอร์ม/นำเข้า) ที่เลขบัตรตรงกับความสัมพันธ์ที่สิ้นสุด → conflict `ENDED_RELATIONSHIP` (นำเข้าจัดเป็น CONFLICT พร้อมเหตุผล “สิ้นสุดการดูแล… กรุณาติดต่อผู้ดูแลระบบ”); account-access request ที่เคยเสนอไว้ถูกเลิกใช้ตาม SR-2. เส้นทางให้ผู้ดูแลระบบรับกลับยังไม่ implement — ต้องมี decision ว่าจะสร้างความสัมพันธ์ใหม่ (ต้องเปลี่ยน unique เป็น partial) หรือเปิดกลับแบบมี audit ก่อนทำ.

## UM-1. จัดการผู้ใช้งานโดย OWNER (Product Owner, 2026-10-22)

หน้า `/app/users` รวมบุคลากร อสม. และผู้ป่วยของโรงพยาบาลไว้ในรายชื่อเดียว และใช้หน้ารายละเอียดรูปแบบเดียวกัน; ส่วนเพิ่มเติมของ [ADR-0020](../adr/0020-self-registration-by-national-id.md) (Addendum UM-1). UM-D6 และ UM-D7 เป็นคำตอบของ Product Owner ระหว่าง implement (2026-10-22). ไม่ใช่การรับรอง UAT.
