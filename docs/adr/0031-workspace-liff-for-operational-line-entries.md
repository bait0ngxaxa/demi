# ADR-0031: Workspace LIFF for operational LINE entries

- Status: Accepted (Product Owner direction, 2026-11-08)
- Date: 2026-11-08
- Supersedes in part: the "ลิงก์เมนูงานเปิด **เว็บ DEMI ปกติ** … ไม่ใช่ LIFF" decision of [Phase LINE-QA.A — Hybrid Quick Action Rich Menu](../phases/PHASE_LINE_QA_A_HYBRID_QUICK_ACTION_RICH_MENU.md), for operational entries launched from LINE only.
- Amends: [ADR-0009](./0009-demi-line-oa-liff-identity-and-messaging.md) decision 1 (one more LIFF app in the same DEMI LINE Login channel). Every other ADR-0009 decision is unchanged.
- Does not change: DEMI authentication, login-return allowlist, Role + Capability + Scope authorization, Account LIFF, Account Link/Unlink/Full Disconnection/Recovery, the MINI App channel and its scoped routes, Rich Menu catalog/role presentation (Option C), notifications, database schema.

## Context

The hybrid Quick Action design opened Patient, OSM and Hospital work from the Rich Menu and HELP Quick Reply as ordinary HTTPS URLs. LINE opens such URLs in its ordinary in-app browser, which shows LINE's browser footer, while the Account LIFF opens in the Full LIFF browser without it. The Product Owner directed that every supported operational workflow launched from the DEMI OA open and stay in a Full-size LIFF browser. This is browser-container behavior chosen by LINE from the URL type; it cannot be fixed with CSS.

Verified platform behavior (LINE LIFF documentation and `@line/liff` 2.31.1 source):

- `https://liff.line.me/<liffId>/<path>?<query>` opens the Endpoint URL (primary redirect) with `liff.state=/<path>?<query>`; `liff.init()` then calls `location.replace()` to Endpoint path + `<path>?<query>` (secondary redirect) and its promise does not settle.
- A bare `https://liff.line.me/<liffId>` primary redirect carries credentials only in the URL **fragment** (`#access_token=…&context_token=…`), which the server cannot see. LINE warns that changing the URL or answering 301/302 before `liff.init()` resolves can break opening, and that the primary redirect URL holds the user's access token.
- With an Endpoint URL that has no path or query, the secondary redirect URL is the origin plus the LIFF URL's additional path, so no second `liff.init()` is required *for the redirect itself*. Independently, LINE states that "LIFF apps must be initialized each time a page is opened", including new pages within the same LIFF app.
- LINE reserves query parameters starting with `liff.` for SDK initialization and LIFF-to-LIFF transitions (`liff.state`, `liff.referrer`, and parameters LINE may add later) and asks apps to leave them untouched until `liff.init()` resolves; `lineAppVersion` may be added on Android ([LIFF URL additional info, 2026-07-16](https://developers.line.biz/en/tips/2026/07/16/liff-url-additional-info/), [LIFF reference](https://developers.line.biz/en/reference/liff/)).
- In `@liff/init` 2.31.1, when the LIFF browser has no access token, `liff.init()` sends the user to LINE Login with the current URL plus `liff.hback=2` as redirect URI, and the secondary redirect keeps `liff.hback` on the destination.
- A LIFF-to-LIFF transition happens when the user follows a link to the other LIFF app (its LIFF URL) from a `Full` LIFF app, and the destination initializes with `liff.init()` ([Opening a LIFF app](https://developers.line.biz/en/docs/liff/opening-liff-app/)). `liff.isInClient()` may be called before `liff.init()` resolves.

## Decision

1. **One new LIFF app, "DEMI Workspace"**, in the existing DEMI LINE Login channel of the existing DEMI Provider. Size **Full**, Endpoint URL `<DEMI_LINE_PUBLIC_ORIGIN>/`, scopes `openid profile`. Its public ID is `NEXT_PUBLIC_DEMI_LINE_WORKSPACE_LIFF_ID`. `NEXT_PUBLIC_DEMI_LINE_LIFF_ID` remains the Account LIFF only.
2. **Configuration is validated, never substituted.** The Workspace LIFF ID must match the LIFF ID format, start with `DEMI_LINE_LOGIN_CHANNEL_ID-` (a LIFF ID is `<channelId>-<suffix>`) and differ from the Account and MINI LIFF IDs. Otherwise it is unavailable; no code path falls back to another LIFF identity. `env:check` validates it once set.
3. **`/` is the Workspace LIFF entry.** It no longer answers with a server redirect. A small client entry loads the LIFF SDK only when LIFF query parameters or LIFF credential fragments are present, lets `liff.init()` consume them first, and otherwise continues ordinary browsers immediately to `/app` (authorized) or `/login`. No continue/reload control may interrupt pending initialization; a timeout cannot cancel SDK work. Invalid or unavailable LIFF entries keep platform parameters untouched and ask the user to close and reopen from LINE. `liff.state` is accepted only for the fixed destinations derived from `LINE_WEB_NAVIGATION_PATHS`; anything else is rejected before initialization. Init is single-flight and bounded (10 s); LINE Login returns have a loop latch; external browsers are never sent to LINE Login (`withLoginOnExternalBrowser: false`). `/` responses are `private, no-store` and `no-referrer`.
4. **Deep links.** `buildLineIntentUrl()` routes operational intents to `https://liff.line.me/<WORKSPACE_LIFF_ID><fixed path>` (Rich Menu URI areas and HELP Quick Reply). Account intents stay on the Account LIFF. `message` and `richmenuswitch` actions are unchanged. Until a valid Workspace LIFF is configured the builder keeps the previous ordinary web URL; this is technical provider configuration, not a business feature switch.
5. **No second application.** The Workspace LIFF is transport only. The secondary redirect opens the existing `/app/...` routes; internal Next.js navigation, server-action redirects and full-document same-origin navigation stay in the same LIFF browser. No `/liff` route tree is added.
6. **LINE identity is not DEMI authentication.** The Workspace entry sends no LIFF token to DEMI and creates no session. Unauthenticated users get the existing DEMI login and the existing exact login-return allowlist; every page keeps its server authorization.
7. **Platform parameters vs. application navigation (remediation 2026-11-08).** At `/` any bounded `liff.*` name, `lineAppVersion` and the LINE Login return markers are platform parameters: recognized, never rewritten or removed, never navigation authority. Only `liff.state` names a destination and it must be a single exact allowlisted value; a non-platform parameter on a LIFF entry still rejects it. Counts and lengths are bounded.
8. **Account navigation is LIFF-aware in both directions.** Workspace → Account: Account links (`/app/line/account`, the recovery nudge, the settings reminder link) open the Account LIFF URL from `buildAccountLiffUrl()` once the Workspace LIFF is initialized. Account → Workspace (round 2): the Account screen's "ใช้งาน DEMI ผ่านเว็บ" link opens the Workspace LIFF URL of the work dashboard from `buildWorkspaceLiffUrl("OPEN_WORK_WORKSPACE")` while the Account LIFF is current, so the Workspace LIFF enters through its own Endpoint and `liff.init()`. Ordinary browsers, MINI sessions and missing configuration keep `/line/account` and `/app`; only the exact Account/Workspace LIFF URL shapes are ever followed. Server rendering always emits the ordinary routes; the client switches after hydration.
9. **Login return survives LINE bookkeeping.** The quick-action return is resolved once in Proxy from the request URL after removing only LINE platform parameters (`liff.*`, `lineAppVersion`, and OAuth markers only with `liffClientId`). Application query segments stay raw and ordered, so repeated, re-encoded, unknown or conflicting parameters still fail the exact allowlist.
10. **Document transport gate (final remediation).** HTML document GET/HEAD requests for `/app`, its descendants and `/login` are internally rewritten to the public `/workspace-liff-document` shell, preserving the visible path, query and fragment. No protected route tree, actor or Patient/Hospital/OSM data is rendered into this document; after required init completes, `router.refresh()` requests the original protected route as RSC in the same document. Ordinary browsers request RSC immediately without loading LIFF. The dedicated render route is not a new LINE Endpoint or a duplicate app tree. Next.js 16.3.0 normally normalizes loopback origins and strips Flight headers in Proxy; the documented `skipProxyUrlNormalize: true` preserves the original URL and headers, so the rewrite stays internal even behind the documented loopback reverse proxy. Only literal `_rsc` transport segments on RSC requests are removed from the derived return-path lookup, without reserializing application query bytes or changing the actual URL. Existing session refresh, protected layout, services, login allowlist and actions still enforce server access. A public-shell branch inside the protected layout is insufficient: production smoke demonstrated that Next can independently render child routes and still emit their redirects. Document selection changes representation only, never access rights; a direct RSC request still encounters all existing authorization.
11. **Separate session presentation, document ownership and initialization.** The existing `{ current, mini, workspace }` session value remains last-app/link presentation only. It never selects SDK initialization. `PerformanceNavigationTiming.type` is no longer read. A root Workspace entry can write one handoff `{ liffId, destination, expires }` before the SDK redirects: only exact existing Workspace destinations (or the fixed `/login` bare-entry fallback), one consumption, 60-second expiry, rejected on mismatch/invalid data; Account/MINI entry invalidates it. A proven Workspace document also prepares a one-shot match for an SDK-owned LINE Login return to its exact current URL, including resource pages; that value is compared only, never followed or used as DEMI `returnTo`. Success or actual SDK rejection clears it; timeout retains it only until expiry because SDK work is not cancelled. A successful document initialization marks that browser history entry with the configured LIFF ID, preserving Next.js history fields and the URL. The existing app/login trees record later SPA entries and pagehide only when this document actually initialized Workspace; they never load/init the SDK. History observation uses the existing Suspense boundary so static routes satisfy Next.js search-parameter prerendering rules. A new document initializes only from that handoff or a marked history entry. Same-document remounts join the actual gateway initialization, including StrictMode; a pending or historical session marker is insufficient. BFCache restoration reuses the initialized document and reasserts presentation; a history restoration that creates a new document goes through the gate. The documented `liff.id` property is only a negative guard against an SDK already configured for another app in this document, never positive evidence that an uninitialized document belongs to Workspace. MINI chain behavior and Account links remain unchanged.
12. **Failure behavior.** Single-flight initialization, the 10-second bound and LINE Login loop latch remain. Rejection or timeout shows explicit Thai close/reopen instructions and no application-controlled link, retry, reload or history mutation. A timed-out SDK may still resolve or redirect; the application never starts a competing init or advances the protected tree from that failed gate. Browser/LINE-owned close, Back and reload remain user actions outside application navigation. Storage failure/malformed handoff never infers LIFF identity or bypasses DEMI auth. A clean ordinary URL keeps web behavior; a platform-bearing callback without reliable ownership remains on explicit close/reopen recovery rather than dropping unconsumed SDK parameters. LIFF restoration availability remains subject to device UAT.
13. **Protected RSC failure after initialization.** `router.refresh()` returns no completion promise. In Next.js 16.3.0, a failed protected RSC fetch (network error or non-RSC response) falls back to a same-URL `location.replace`. That new document goes through the gate again and initializes once from its marked history entry; the protected tree then renders. A failure that persists would otherwise reload and re-initialize without end. Therefore a non-authoritative per-tab latch counts gate continuations per exact path and query. After three in 60 seconds, the next document neither initializes LIFF nor requests RSC. It shows explicit Thai recovery text with no application-controlled link, retry or reload. Any rendered protected or login tree clears the latch. Unavailable storage disables only the latch. Neither the latch nor its absence grants access.

## Alternatives considered

- **Dedicated gateway Endpoint (e.g. `/line/workspace`)**: rejected. LIFF prepends the Endpoint path to the deep-link path (`/line/workspace/app/...`), so either every route moves or destinations travel as query intents to a client router. The root Endpoint keeps the existing routes and their login returns exactly.
- **Keep the server redirect on `/` and only add a gateway when `liff.state` is present**: rejected. A bare LIFF launch has no query; a 307 would bypass `liff.init()` and carry the credential fragment into `/app`'s URL.
- **Authenticate DEMI from the LIFF ID token**: rejected by ADR-0009 and by owner direction.
- **CSS to hide the footer**: impossible; the footer belongs to LINE's browser.

## Consequences

- Ordinary visits to `/` take one client-side hop instead of a 307; transport screens have no active navigation controls while JavaScript can run SDK work, because even a bare launch can carry fragment credentials. The ordinary root retains its inert-when-scripting-enabled `noscript` web exit. App/login document loads now require JavaScript and one RSC request; without scripting the gate explicitly asks to enable it. Ordinary browsers still load no LIFF SDK. The protected route tree is unchanged.
- Opening the Workspace LIFF in LINE grants the existing DEMI LINE Login channel's `openid profile` consent, the same channel the Account LIFF already uses. Full Disconnection already deauthorizes that channel; reopening the Workspace LIFF afterwards can grant consent again. The unlinked Rich Menu has no Workspace entries, so this requires an old message or a typed LIFF URL.
- Messages and user-bound Rich Menus issued before rollout keep ordinary web URLs and still open in the ordinary in-app browser until Rich Menus are reconciled and repaired; past chat messages cannot be changed.
- `NEXT_PUBLIC_DEMI_LINE_WORKSPACE_LIFF_ID` is inlined at build time; the deployed build and the reconcile script must use the same value.
- Real-device behavior (footer absence, cross-LIFF transitions, cookie persistence) is verified only by the UAT in [LINE_WORKSPACE_LIFF_UAT](../operations/LINE_WORKSPACE_LIFF_UAT.md); automated tests mock the SDK.

## Final remediation evidence

The round-3 decision to retain the initialization/redirect race is superseded. Primary redirect processing, secondary-document initialization and SPA navigation are separate contracts. Root initialization does not prove safety of a later document's URL mutation. The root Endpoint having no additional path/query avoids one special redirect-construction requirement; it does not exempt a new LIFF document from initialization or permit a router to interrupt it. LINE's [developing guide](https://developers.line.biz/en/docs/liff/developing-liff-apps/), [opening guide](https://developers.line.biz/en/docs/liff/opening-liff-app/), [API reference](https://developers.line.biz/en/reference/liff/) and [2026-07-16 guidance](https://developers.line.biz/en/tips/2026/07/16/liff-url-additional-info/) were checked against the installed Next.js **16.3.0** and `@line/liff` / `@liff/init` **2.31.1**.

The production Next smoke now checks an initial public document with no auth redirect, then separately requests RSC and verifies the existing exact login return. The Playwright harness runs the actual Next route tree, protected layout, Supabase SSR session cookies, DEMI login server action and disposable PostgreSQL fixture. Its isolated source copy aliases only the external LINE SDK; a local Supabase provider returns signed synthetic JWTs and current-session responses. No production test flag, session bypass or mock loader is introduced. The harness logs document, module, init, SDK redirect, RSC and History API events. Delayed module loading and delayed init both precede any protected RSC/navigation; timeout and rejection do not advance. Browser tests are Chromium evidence, not Android/iOS LINE evidence.

See [the remediation evidence and commands](../engineering/WORKSPACE_LIFF_LIFECYCLE_REMEDIATION.md) for the 13-step lifecycle timeline, claims A/B/C, SDK source paths, regression matrix, reproducible old-HEAD failure and test limitations.

## Open questions for UAT

- `target="_blank"` links (legal documents, evidence images, workforce slips) may open outside the LIFF browser; they are document views, not workflow steps, and are left unchanged unless UAT shows a broken return.
- Whether session storage survives LIFF-to-LIFF transitions and returns on each OS and LINE version (the context assumes it may survive and records each app's own entry; if it does not, links fall back to ordinary routes).
- If session storage is unavailable, no presentation context or handoff is recorded. Account links fall back to ordinary routes. A clean ordinary URL still continues on the web. A secondary or callback document that carries LINE platform parameters has no reliable ownership evidence and stays on close/reopen recovery (decision 12) rather than continuing without `liff.init()`. How often this occurs on each OS and LINE version is a UAT question.
- Whether a LIFF-to-LIFF transition back from the Account LIFF restores the Workspace page from BFCache or reloads it depends on LINE version and OS.
- The MINI gateway classifier still rejects `lineAppVersion`; it is outside this ADR's scope and tracked separately.
