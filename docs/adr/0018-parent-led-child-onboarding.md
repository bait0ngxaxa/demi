# ADR-0018: ADMIN Bulk Parent Registration and Parent-led Child Onboarding

- Status: Accepted (Product Owner, 2026-10-21)
- Date: 2026-10-21
- Supersedes in part: [ADR-0003](./0003-hospital-led-onboarding.md) (Child facilities leave the public onboarding flow), [ADR-0015](./0015-admin-governed-hospital-network.md) (a Parent OWNER may register CHILD facilities into its own network) and [ADR-0016](./0016-network-patient-read.md) ("a Child must be ACTIVE before a Parent can attach it" no longer holds for Parent-created Children). Resolves WB-PD-12. Builds on [ADR-0008](./0008-workforce-provisioning-and-activation.md), [ADR-0012](./0012-global-credential-recovery-proof.md) and [ADR-0017](./0017-retire-hospital-master.md).

## Context

After ADR-0017 every Hospital is registered by Platform ADMIN one at a time, and the first OWNER of every Hospital, Parent or Child, comes from the public "choose a Hospital and apply" page. The customer registers its main Hospitals centrally but wants each Parent to bring in its own รพ.สต./PCU/PCC, which ADMIN does not know in advance, and the public list let anyone apply as OWNER of any unclaimed Hospital.

## Decision (O-D1..O-D9)

- **O-D1** Platform ADMIN registers Parent Hospitals one at a time (existing form) or in bulk from a UTF-8 CSV (`name,hospitalCode`, optional BOM, code optional → generated `H-XXXXXX`, at most 200 rows). The file is previewed first: each row is OK, invalid, a code repeated in the file, a code already registered, or a name similar (whitespace/case-normalised) to an existing Hospital or another row, which needs explicit per-row confirmation. Apply creates every row as `PENDING_VERIFICATION` with role PARENT in one serializable transaction, all-or-nothing, with one `hospital.created` audit per row and one `hospital.bulk_registered` summary (row count only). Apply is idempotent per batch submission nonce: row *i* is stored with an N1 `registrationNonce` derived deterministically from (batch nonce, *i*); a replay by the same ADMIN with the same rows returns the original Hospitals and creates nothing, any other reuse is a conflict. Parent onboarding is unchanged: public application → ADMIN review → first OWNER.
- **O-D2** Child facilities are not onboarded publicly. The public list, the code lookup, submission and ADMIN approval accept only a `PENDING_VERIFICATION` Hospital with role PARENT that was never the Child of any area (active or ended), enforced on the server. The active Parent OWNER creates the Child and invites its first OWNER in one serializable transaction: Hospital (`PENDING_VERIFICATION`, `registeredByUserId` = the OWNER, `registeredForParentHospitalId` = the Parent, idempotent per submission nonce) → role CHILD → active `HospitalServiceArea` → OWNER membership → invitation. Both sides see "รอเปิดใช้งาน" without a separate attach step.
- **O-D3** For Parent-created Children only, attachment precedes activation. Network Patient reads and Parent reports still require the Child to be ACTIVE (existing predicates, unchanged), so the Parent sees nothing of a pending Child but its name, code and invitation state.
- **O-D4** The Parent OWNER invites only the Child's first OWNER, and a replacement OWNER when an ACTIVE Child has no ACTIVE OWNER. The Child's own OWNER manages Child staff and OSMs (ADR-0008 unchanged); the Parent never provisions Child workforce.
- **O-D5** For a currently attached Child the Parent may: rename it (only the Parent; the Child's own OWNER has no rename path; audited, optimistic concurrency); while it is pending or ownerless, issue a new REMOTE/ASSISTED link, revoke the link, change the invitee (the open invitation ends first) or, while pending and registered by this Parent, cancel it (one transaction: links revoked, open memberships ENDED, area ended with the reason, Hospital RETIRED with `HospitalRetirementEvent`, actor = the Parent OWNER); invite a replacement OWNER. Not allowed: suspend/restore, contact edits, Child workforce, transfer (ADMIN only, ADR-0015).
- **O-D6** Invitations reuse the workforce activation capability: one hash-only, single-use token per User; national-ID check with 5 failures → revoke; REMOTE link/QR valid 24 h (staff/OSM links keep 72 h), ASSISTED 15 min; the same provider claim, quarantine and reconciliation. The new purpose `CHILD_OWNER_ONBOARDING` (context kind `CHILD_OWNER`, SQL CHECK) is a special case inside completion: it is the only purpose whose Hospital may still be `PENDING_VERIFICATION`; inside the completing transaction it re-checks that the Child still has role CHILD and is pending (or ACTIVE without an ACTIVE OWNER for a replacement), that the area recorded at invitation (`HospitalMembership.invitedViaServiceAreaId`) is still active, that the membership is still PROVISIONED and that the inviting/issuing OWNER still holds that Parent. Success makes the User, the OWNER membership and (for a first OWNER) the Hospital ACTIVE, audited `hospital.child_onboarded` / `hospital.child_owner_replaced`. Every other purpose keeps the Hospital-ACTIVE guard unchanged. If the invitee already has an ACTIVE account, nothing is granted and no token is issued: the membership is `INVITED` and the person accepts or declines on their own work home in their own session (ADR-0012: an ID typed by someone else is not consent). Acceptance re-checks the same context; a decline ENDs the membership with `invitationDeclinedAt`, which the Parent sees. Existing PROVISIONED (with pending scope elsewhere), INVITED, SUSPENDED, ADMIN or provider-ambiguous accounts fail closed exactly as workforce provisioning does.
- **O-D7** Parent area and Child management stay OWNER-only (no MEMBER delegation).
- **O-D8** Existing free ACTIVE CHILD facilities can still be attached through the existing attach flow. Platform ADMIN keeps role, transfer, end and retire powers and may still register a CHILD for exceptions (*narrowed by the amendment below: ADMIN registers Parents only*). ADMIN retire now also refuses any Hospital that is the Parent or Child of an active area (`ACTIVE_SERVICE_AREA`).
- **O-D9** Former Hospital Master data is out of scope: existing PENDING rows are not adopted, migrated or special-cased; ADMIN retires them with N1 bulk retire.

## Consequences

- Migrations `20261101100000_workforce_activation_child_owner_purpose` (enum value) and `20261101110000_parent_led_child_onboarding` (additive: `Hospital.registeredForParentHospitalId`, `HospitalMembership.invitedByUserId`/`invitedViaServiceAreaId`/`invitationDeclinedAt` with a consistency CHECK, and the purpose-aware `WorkforceActivation_context_check`). Existing rows keep NULL; no backfill.
- Platform ADMIN sees provenance ("สร้างโดยแม่ข่าย …") on pending Children and can retire a Parent-created Child only after its area ended.
- The synthetic demo seed now follows this flow: the demo Parent is onboarded publicly and creates its two Children (generated codes), whose OWNERs activate through the link; reset deletes demo-registered Children. Pre-ADR-0018 `<code>-A`/`<code>-B` rows are left untouched.
- Residual risks: a Parent can create duplicate or fictitious facilities (mitigated by ADMIN visibility of provenance, retire and audit); an invitation link can be intercepted (mitigated by the national-ID check, the 5-failure revoke and expiry). An invitee who is already an open member of the Child (e.g. its MEMBER after the OWNER left) cannot be invited as replacement OWNER; that fails closed.

## Amendment — 2026-10-21 (Product Owner)

- O-D8 is narrowed: Platform ADMIN registers **Parent Hospitals only**. The single registration form and `createHospital` no longer take a network role (a supplied `networkRole` is rejected as invalid input); every ADMIN-registered Hospital gets role PARENT. Child facilities come only from their Parent OWNER (O-D2). ADMIN keeps role changes on an existing Hospital's detail page, transfer, end and retire.
- The bulk import offers a downloadable template (`/templates/hospital-parent-import-template.csv`: UTF-8 with BOM, header `name` only, no sample rows) and explains how to fill and save it on the page.
- Hospital codes are always generated (`H-XXXXXX`) on every registration path: the ADMIN form, the bulk file and the Parent's Child form have no code field, the services reject a supplied `hospitalCode`, and the import file has a single `name` column (a file with the earlier `name,hospitalCode` header is refused). The preview therefore no longer checks repeated or already-registered codes.
