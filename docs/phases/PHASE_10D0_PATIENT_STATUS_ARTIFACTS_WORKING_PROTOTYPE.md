# Phase 10D.0 — Relationship-Level Patient Status Evidence / Artifact Working Prototype

## 1. Status

Implemented as a bounded, provisional working prototype. This slice is requirement validation, not a final customer-approved media or retention policy.

The ownership decision is provisional: one artifact has exactly one concrete business owner, `PatientHospitalRelationship`.

## 2. Goal

Demonstrate the concrete legacy behavior that exists—patient/relationship status evidence images—inside the DEMI rewrite while preserving the current architecture:

- exact relationship ownership;
- server-side Role + Capability + Scope authorization;
- private binary storage;
- PostgreSQL metadata separate from binary content;
- short-lived authorized access;
- bounded audit;
- explicit PostgreSQL/storage consistency behavior.

## 3. Legacy evidence

The pinned legacy implementation was inspected as behavioral evidence only. Legacy status tracking presents an image gallery with an optional caption and image access, and it uses a long-lived signed access pattern. Legacy Baseline and Follow-up pages also contain separate image/URL behavior.

The rewrite does not copy those storage paths, global user ownership, permanent access behavior, or embedded Follow-up URL fields. The legacy behavior confirms an evidence/photo workflow; it does not decide the new owner or authorization model.

## 4. Relationship-level ownership decision

The first Phase 10D slice is relationship-level status evidence only:

```text
Person → PatientProfile → PatientHospitalRelationship → PatientEvidenceArtifact → private object
```

`PatientEvidenceArtifact.patientHospitalRelationshipId` is the single business owner and the metadata authorization anchor. The object key is opaque and generated by the server. It does not contain Patient name, HN, national ID, phone number, Hospital name, or a relationship identifier.

This owner is provisional for the prototype. A generic owner abstraction was intentionally not created.

## 5. Explicit exclusions of Baseline and Follow-up ownership

The artifact model contains no `baselineId`, `followupId`, `appointmentId`, `screeningId`, or `goalPlanId`. No `PatientBaseline.artifacts`, `PatientFollowup.artifacts`, nullable polymorphic owner columns, `ownerType`, or `ownerId` was added.

Baseline and Follow-up behavior is unchanged. Whether either domain needs event-specific evidence remains an open customer requirement.

## 6. Artifact metadata model

The forward-only Prisma migration adds `PatientEvidenceArtifact` with:

- `id` — UUID primary key;
- `patientHospitalRelationshipId` — required relationship foreign key;
- `storageObjectKey` — unique private-provider object key;
- `mediaType` — validated `image/jpeg`, `image/png`, or `image/webp`;
- `byteSize` — actual uploaded byte count;
- `contentSha256` — lowercase SHA-256 of the actual bytes;
- `caption` — optional trimmed text, maximum 500 characters;
- `createdByUserId` — required server-derived creator foreign key;
- `createdAt` — PostgreSQL timestamp.

Both foreign keys use restrictive deletion behavior. The relationship/created-at index supports bounded newest-first listing and the object key is unique.

There is intentionally no lifecycle enum. The prototype is append-only: create, list, and view. Delete, replacement, supersession, restore, and tombstoning are open requirements.

## 7. Binary-storage separation

PostgreSQL stores metadata and the private object key only. It never stores a public URL, signed URL, CDN URL, download URL, or temporary access token. The original browser filename is ignored and is not authoritative or persisted.

The application uses a small server-only `PatientEvidenceStorage` boundary. The concrete implementation is `SupabasePatientEvidenceStorage`; it is not a provider registry or generic document-management abstraction. `removeObject` exists only for best-effort creation compensation and is not exposed as a product deletion workflow.

## 8. Private Supabase Storage boundary

The concrete bucket is configured through `SUPABASE_PATIENT_EVIDENCE_BUCKET`, with `patient-evidence` as the documented development/demo value. The bucket must be private. The adapter uses the server-only Supabase service-role client for upload, short-lived signed access, and compensation removal.

Application authorization remains authoritative. A privileged storage client is never imported by UI code, never sent to the browser, and is invoked only after relationship authorization in the application service/query boundary. The implementation does not call `getPublicUrl()`.

Reference documentation consulted for the installed packages and selected APIs:

- [Next.js Route Handlers](https://nextjs.org/docs/app/api-reference/file-conventions/route)
- [Supabase Storage upload](https://supabase.com/docs/reference/javascript/storage-from-upload)
- [Supabase Storage signed URLs](https://supabase.com/docs/reference/javascript/storage-from-createsignedurl)
- [Supabase Storage bucket fundamentals](https://supabase.com/docs/guides/storage/buckets/fundamentals)

## 9. Supported image policy

The prototype accepts only these exact declared and detected formats:

- `image/jpeg` — JPEG signature;
- `image/png` — PNG signature;
- `image/webp` — RIFF/WEBP signature.

The current client may select a source image up to 25 MiB. Before upload, the browser decodes supported sources, preserves aspect ratio, limits the longest edge to 2,560 pixels without upscaling, and sends only the normalized result. A suitable source already no larger than 8 MiB and within the dimension limit may retain its original bytes; a source that needs processing is encoded as JPEG using a small bounded set of quality/dimension attempts.

The authoritative server-side normalized-file maximum is 8 MiB (`8 * 1024 * 1024` bytes). Empty files, oversized normalized files, unsupported media, malformed signatures, and declared/signature mismatches are rejected independently of client processing. PDF, SVG, arbitrary `image/*`, HEIC/HEIF, video, audio, archives, office files, and generic binary data are rejected. The accepted formats and limits remain provisional requirement-validation policy, not customer-approved media, malware, retention, or compliance policy. No server-side transcoding, OCR, thumbnail generation, or derivative storage is performed.

## 10. Server-side content validation

The multipart `File.type`, Content-Type header, extension, and original filename are not trusted as proof of content. The server reads the bytes, checks only the three supported signatures, and requires the detected type to equal the declared media type. SHA-256 is calculated from those same bytes and stored as integrity metadata only.

The hash is not used to infer clinical duplicate meaning, reject repeated evidence, or create content-addressed storage.

## 11. Authorization and capability matrix

The provisional capabilities are `patient-artifact:read` and `patient-artifact:create`. Delete and supersede capabilities do not exist in this phase.

| Actor path | Read | Create |
| --- | --- | --- |
| Active direct Hospital OWNER | Allowed | Allowed |
| Active direct Hospital MEMBER | Allowed | Allowed |
| Exact active assigned OSM | Allowed | Allowed |
| OSM–Hospital relationship without exact Patient assignment | NotFound/hidden | NotFound/hidden |
| Wrong Hospital | NotFound/hidden | NotFound/hidden |
| ADMIN-only | Forbidden | Forbidden |
| ADMIN plus valid direct Hospital path | Allowed | Allowed |
| ADMIN plus valid exact OSM path | Allowed | Allowed |
| Hospital hierarchy only | Denied | Denied |
| Profession only | Denied | Denied |
| PATIENT self-service | Denied/deferred | Denied/deferred |

The current authoritative User, role, active Hospital status, direct membership, OSM–Hospital relationship, and exact active Patient assignment are reloaded server-side for sensitive creation. `createdByUserId` is always derived from that authoritative actor.

## 12. Anti-enumeration

Actors with no possible artifact role path, such as ADMIN-only or PATIENT-only actors, receive `ForbiddenError` before an unrestricted relationship lookup.

Potentially valid Hospital/OSM actors use an authorization-scoped relationship query. Wrong-Hospital, unassigned OSM, inaccessible, and nonexistent relationship identifiers resolve as `NotFoundError`. The application does not first load an unrestricted relationship and then reveal whether it exists.

## 13. Upload workflow

The upload boundary is:

`POST /app/patients/[relationshipId]/evidence/upload`

It is a narrow authenticated multipart Route Handler. Route Handler transport was selected after checking the installed Next.js behavior because Server Actions have a default request body limit and changing a global limit would be an unnecessarily broad transport change. No global Next.js request limit was changed for this phase. The endpoint uses the pinned `@fastify/busboy` `3.2.1` streaming parser only at this upload boundary; it supports Node stream limits without introducing a generic upload subsystem.

`Content-Length` is only a cheap early rejection for an obviously oversized declaration. The route authenticates, resolves the route relationship ID, and pre-authorizes exact `patient-artifact:create` access before consuming `request.body`. It then converts the Web request stream to a bounded Node stream. The total multipart request is limited to `8 MiB + 128 KiB`; the 128 KiB allowance is bounded overhead for two small multipart parts, their headers/boundaries, and the caption field. Busboy independently limits the actual normalized file stream to 8 MiB, one file, one caption, two parts, bounded field/header sizes, and rejects unknown or duplicate fields. Therefore a streamed or understated/no-Content-Length request is still rejected when the actual body or file crosses its limit, without waiting for an unbounded `formData()`/`arrayBuffer()` buffer. The service/schema validation remains a second authoritative layer, and both the create service and the PostgreSQL transaction re-authorize the exact relationship after this transport pre-authorization.

The application service performs the following bounded workflow:

1. Reject an obviously oversized declared Content-Length when present; this is only an optimization.
2. Authenticate the actor and resolve the relationship route parameter.
3. Pre-authorize exact relationship create access with `PATIENT_ARTIFACT_CREATE_CAPABILITY`.
4. Stream and bound the multipart request, accepting only one `file` and at most one `caption` field.
5. Normalize the caption and validate bytes, size, signature, media type, and SHA-256.
6. Generate an opaque artifact UUID and `relationship-evidence/<artifact-id>` object key.
7. Upload the bytes to the configured private bucket through the storage adapter.
8. Run the PostgreSQL transaction for metadata and audit, including its authoritative access re-check.
9. Revalidate the evidence page and relationship detail path.
10. Return only bounded artifact/relationship identifiers.

The browser does not submit owner type, relationship ownership, Hospital, creator, media type, object key, or authoritative user identifiers.

## 14. PostgreSQL transaction boundary

Supabase Storage and PostgreSQL cannot participate in one atomic database transaction. The implementation does not claim that they can.

Inside one Prisma transaction, `PatientEvidenceArtifact` creation and `patient_evidence_artifact.created` audit creation commit or roll back together. The transaction re-resolves the exact relationship and authoritative actor so a permission change between the preflight and metadata write cannot silently create an artifact under stale authority.

## 15. Storage compensation behavior

- If storage upload fails, no metadata or audit transaction is started.
- If metadata or audit fails after upload, the service attempts to remove only the newly generated object key.
- If compensation succeeds, the original persistence failure is returned as a safe failure.
- If compensation also fails, the operation still fails, no metadata row claims ownership, and only a safe operational category plus opaque artifact ID is logged through the existing minimal logging boundary.

An orphaned private object with no metadata is not reachable through the application. Orphan reconciliation remains an operational hardening concern for a future phase; no fake metadata or success response is created.

## 16. Audit boundary

One bounded creation event is recorded atomically with metadata:

`patient_evidence_artifact.created` / `PatientEvidenceArtifact`

Audit metadata contains only the artifact ID and relationship ID. The standard actor field contains the authoritative actor ID. Caption, original filename, binary content, SHA-256, Patient name, HN, clinical values, storage key, bucket credentials, signed URL, and access token are excluded.

## 17. List projection

`GET` page data is loaded through a relationship-scoped bounded query with a newest-first limit of 50. The projection contains only:

```text
id
patientHospitalRelationshipId
mediaType
byteSize
caption
createdAt
creator.id
creator.displayName
```

It excludes storage keys/secrets, signed URLs, raw Users, auth subjects, roles, memberships, identity hashes, and unrelated relationship data.

## 18. Short-lived binary access

The protected content boundary is:

`GET /app/patients/[relationshipId]/evidence/[artifactId]/content`

The route authenticates, authorizes the exact relationship, resolves the artifact with both artifact ID and relationship ID, and only then asks Supabase Storage for a 300-second signed URL. The URL is returned as a redirect to the browser, is not persisted, and is not placed in audit, logs, cookies, local storage, or application metadata. A guessed artifact ID from another relationship cannot bypass the relationship predicate.

## 19. UI workflow

Patient Detail includes a small Thai entry point:

> หลักฐาน / รูปภาพสถานะ  
> ดูหลักฐานและรูปภาพที่เกี่ยวข้องกับการดูแลผู้ป่วยรายนี้

The relationship-scoped Evidence page shows Patient name, HN, Hospital, a create form when `patient-artifact:create` is allowed, and newest-first evidence cards. The form accepts one JPEG, PNG, or WEBP source up to 25 MiB and an optional 500-character caption, explains that the image is reduced automatically, and distinguishes client preparation from upload progress.

Cards use the protected content route for previews and the same route for a `ดูรูป` action. Captions use normal React escaping. There is no delete, replace, supersede, restore, bulk upload, wide table, or complex media manager. The form disables controls during upload, displays progress/failure feedback, and stacks safely on mobile screens.

## 20. Privacy and security boundary

- Service-role credentials remain server-only and are not `NEXT_PUBLIC_*` values.
- Bucket and object path are selected by server configuration/service code, not the browser.
- Original filenames and sensitive identifiers do not become storage keys or audit metadata.
- SVG and raw HTML are not accepted or rendered.
- Signed URLs are short-lived and generated after every independent authorization check.
- Client-facing errors are safe Thai categories; Supabase, Prisma, SQL, stack traces, internal paths, tokens, and bucket internals are not returned.
- No user-supplied clinical classification or `PatientStatus` is inferred from an image or caption.

## 21. Explicit non-goals

This phase does not implement Baseline, Follow-up, Screening, Goal, Appointment, or Patient Profile attachments; generic polymorphic attachments; document management; PDF/Word/Excel; arbitrary files; folders/tags/categories; bulk upload; Patient self-service; delete; replace; supersede; lifecycle/retention automation; malware scanning; server-side image processing; HEIC conversion; OCR; explicit EXIF controls; thumbnails/derivatives; notifications; dashboards; statistics; reports; or clinical status classification.

## 23. Operational Supabase bucket and environment setup

Supabase Storage provisioning is deliberately outside Prisma migrations. The normal PostgreSQL migration creates only `PatientEvidenceArtifact`; it does not reference or create the Supabase `storage` schema.

Configure the application server with:

```text
NEXT_PUBLIC_SUPABASE_URL=<server-side Supabase project URL>
NEXT_PUBLIC_SUPABASE_ANON_KEY=<existing Supabase publishable/anon key>
SUPABASE_SERVICE_ROLE_KEY=<server-only service-role key>
SUPABASE_PATIENT_EVIDENCE_BUCKET=patient-evidence
```

Development/demo/production operators must create a bucket named by `SUPABASE_PATIENT_EVIDENCE_BUCKET` using the current Supabase Dashboard or the current official Supabase provisioning mechanism, then verify that the bucket is private and does not allow public reads. Configure the bucket/object policy for the provisional image types and 8 MiB normalized application limit. Do not put real secrets in `.env.example`, source, tests, or browser bundles.

The service-role key is required only on the trusted server boundary. It must never be exposed through a `NEXT_PUBLIC_*` variable or shipped to the browser. A configured bucket is an operational prerequisite for manual upload smoke testing; normal unit and PostgreSQL integration tests use a fake adapter.
