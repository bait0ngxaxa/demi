## 2. Work Package A — Hospital data contract

### 2.1 Shared scope, population, grain และ state rules

ทุก row ในตารางต่อไปนี้ใช้ exact server-authorized Hospital H. Relationship R ต้องมี `hospitalId=H`; Program P ต้องมี `patientHospitalRelationshipId=R.id`. Child facts ต้อง match P และ R; Baseline ต้อง match `P.initialBaselineId` และ R. ห้าม join Person เพื่ออ่าน relationship ของ Hospital อื่น. Hospital hierarchy ไม่ใช่ Patient scope.

Population **ยัง proposed**: ACTIVE Hospital, eligible relationship ตาม D01, eligible ACTIVE/COMPLETED Programs ตาม D01/D02. Directory/Program access ปัจจุบันตรวจ PATIENT role แต่ไม่ถือว่าทุก Patient ต้อง activate; ห้ามเพิ่ม ACTIVE Patient-only filter โดยเดา. Relationship ไม่มี status/start/end eligibility fields ใน schema; `createdAt/updatedAt` ไม่ใช่ clinical/relationship effective history. ต้องให้ operations ตัดสิน eligibility ที่พิสูจน์จาก source ได้; ถ้าต้อง historical status ที่ไม่มี source ให้หยุดแยก requirement.

Grain: schema unique `(patientProfileId,hospitalId)`, PatientProfile unique personId; ภายใต้ invariant ปัจจุบัน relationship count อาจเท่ากับ distinct Person ใน Hospital เดียว แต่ **ไม่ใช่ semantic approval** ให้เปลี่ยนชื่อเป็น unique Person count. หลาย Programs ทำให้ Program count ต่างจาก relationship count; joins 1:N ต้องไม่นับซ้ำ. ไม่ dedup/เชื่อม population ข้าม Hospital. Aggregate denominator/version/time ต้องอนุมัติแยกจาก list population.

Freshness: values เป็น source state ที่อ่านใน request; ไม่เป็น clinical encounter date หรือ coherent snapshot โดยอัตโนมัติ. `readStartedAt/readCompletedAt` เป็น candidate server read-window metadata เท่านั้น; `dataAsOf` ใช้เมื่อมี proof ของ snapshot จริง. ทุก metric ต้องมี approved definition/version, population, grain, source-time policy, exclusions, missing/suppression และ synthetic examples ก่อน publish.

States: source absent → MISSING; existing nullable field → NOT_RECORDED; recorded zero → RECORDED(0) เมื่อ source validation ยอมรับจริง. Empty eligible set ให้ count 0 ได้เฉพาะ query ที่ authorized และสำเร็จตาม approved population. Unsupported/source-blocked → UNAVAILABLE candidate; privacy suppression/withheld ต้องไม่คืน hidden value หรือ existence reason. DENIED เป็น access failure ไม่มี rows/counts; ไม่ใช่ empty success. NA ใช้เฉพาะ source/rule ที่อนุมัติ. Existing `ReportFact` ยังไม่มี withheld/denied variants; future DTO state contract ต้อง review แยก ไม่แก้ exact projection โดยนัย.

Availability ด้านล่างหมายถึง source readiness เท่านั้น: **AFTER_APPROVAL** = implementable fact เมื่อ gates ปิด; **SOURCE_BLOCKED** = ขาด fact/linkage หรือ approved derivation; ทุก Hospital field/count ยัง **DISCLOSURE_BLOCKED** จน approved allowlist/policy. Optional omitted fields ไม่ขวาง minimal slice หาก customer/authority ลงนามยอมรับ omission ตาม D07.

## 3. Work Package B — Proposed bounded Hospital read

### 3.1 Capability proposal (ไม่มี runtime policy change)

Reuse proposed `report:hospital:summary:read` from 18C.1B for approved non-identifying metrics of **one exact Hospital**. Propose `report:hospital:program-list:read` for bounded Program-grain discovery/navigation within **one exact Hospital**, limited approved identity/lifecycle fields. Target: `{hospitalId}` resolved against authoritative current Hospital and direct membership; field set/population/policy version governed by signed contract. Neither implies the other, `report:program:read`, `patient:read`, Global, Network, mutation or export. Do not invent a generic grant table or profession-based entitlement before approval.

| Actor context | Summary/list candidate rule | Existing exact Program rule retained |
| --- | --- | --- |
| HOSPITAL + direct active OWNER | Allow only if capability assignment and field/population contract explicitly approved; OWNER not automatic reporting authority | Active direct membership in ACTIVE H allows exact read through existing resolver |
| HOSPITAL + direct active MEMBER with approved capability | Allow only that operation/H/fields; mechanism and issuer require approval | Current exact policy allows direct active MEMBER |
| MEMBER without that capability | Deny cohort/summary despite existing patient/program read | Exact policy unchanged; list denial need not revoke separately accepted exact read |
| OSM, even exact assigned | Deny Hospital cohort/summary candidate; no Hospital membership substitution | Existing exact assigned Program access remains; no cohort enumeration implied |
| PATIENT / ADMIN-only | Deny Hospital reporting; ADMIN is Platform context | Denied by existing routine report policy |
| Inactive User, suspended/inactive membership/Hospital, missing actor, unknown capability, wrong H, parent/sibling-only membership | Fail closed, no rows/counts/existence result | Current resolver/policy boundaries remain |
| Multi-role | Evaluate explicit Hospital operation and direct approved membership; ADMIN/OSM/PATIENT roles cannot contribute a bypass | Existing exact report evaluates its own policy |

Approvers: Product Owner + Hospital operations/data owner define eligible OWNER/MEMBER operation matrix and issuer/revocation; Security/Privacy/Data Controller approve purpose, minimum fields, disclosure, audit and denial; Architecture reviews enforcement. No such approved cohort assignment is present at inspected HEAD.

### 3.2 Read sequence and query bounds

1. Server boundary uses current authenticated actor (`getProtectedApplicationActor`/Actor service); strict validated input: Hospital UUID locator, bounded page size, cursor, approved filter vocabulary only. Reject unknown properties, arrays, malformed/oversized inputs; no raw SQL/client select/field list.
2. Resolve current User ACTIVE + HOSPITAL role, direct ACTIVE OWNER/MEMBER membership and Hospital ACTIVE from authoritative DB; check **approved reporting capability**, not just existing Directory eligibility. Browser Hospital ID narrows authorized scope; never supplies it.
