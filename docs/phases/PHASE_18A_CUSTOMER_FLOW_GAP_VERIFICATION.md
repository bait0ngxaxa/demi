## 1. ข้อสรุป

ระบบปัจจุบันรองรับแกนของ Patient self-service, Hospital/OSM care recording, appointment coordination และ per-Program factual readback ในระดับ source code หลายส่วนแล้ว แต่ยังตอบ “ได้ครบ” ต่อโจทย์ลูกค้าไม่ได้: การบันทึกผลไม่เท่ากับหลักฐานว่าให้บริการจริง, Goal Plan คือ target ไม่ใช่ achievement, Follow-up timestamp เป็นเวลาบันทึกไม่ใช่วันพบผู้ป่วย, Program completion ไม่ใช่ clinical outcome และ assignment ปัจจุบันไม่ใช่หลักฐานผู้ดูแลย้อนหลัง

จุดที่ขวางการยืนยัน end-to-end คือ flow บางช่วงยังเป็น preference/request หรือไม่เก็บ event ที่ลูกค้าต้องการ, family scope จำกัด, Hospital responsibility area ยังเปิด, manual/customer UAT ยังไม่ปิด และ reporting ยังมีเพียง exact-Program read ไม่มี cohort/export authorization หรือ coherent two-sheet snapshot contract. ผลตรวจรายละเอียดราย flow อยู่ใน Section 4; data lineage อยู่ใน [Phase 18AB gap backlog](./PHASE_18AB_VERIFIED_GAP_BACKLOG.md).

### 2.1 Authorization invariant ที่ใช้ตลอดเอกสาร

- PATIENT อ่าน/แก้ได้เฉพาะ self-scope ที่ server resolve จาก authenticated identity.
- Family/Caregiver ต้องมี relationship และ grant ที่ระบุ resource; ไม่ได้ authority จากความเป็นญาติหรือ PATIENT role โดยอัตโนมัติ.
- OSM clinical read/write ต้องมี exact active PatientOsmAssignment และ active OsmHospitalRelationship; OSM role, geography หรือ Hospital association อย่างเดียวไม่พอ.
- HOSPITAL care scope ต้องเป็น direct active OWNER/MEMBER ของ Hospital นั้น. Hospital OWNER ไม่ใช่ Platform ADMIN; parent/child Hospital relation ไม่สืบทอด Patient access.
- Platform ADMIN มี governance/onboarding scope; ไม่มี routine patient-care/reporting access.
- `report:program:read` ใช้กับ exact Program เท่านั้น; ไม่ใช่ Hospital cohort/export capability. Hospital Network aggregation ก็ไม่ให้สิทธิ์อ่าน Patient รายบุคคล.

อ้างอิง: [Phase 17A Section 4](./PHASE_17A_CUSTOMER_FLOW_CANONICALIZATION_UAT_CONTRACT.md), `src/modules/patient-self/policies/patient-self-policy.ts`, `src/modules/patient-assignment`, `src/modules/workforce/policies/hospital-owner-policy.ts`, `src/modules/reporting/policies/program-report-policy.ts` และ [ADR-0001–0009](../adr/README.md).

## 6. คำตอบตาม customer outcome

- **Fully represented:** provision → activation → own Patient workspace; exact-scope Patient/Hospital/OSM read/write ที่ contract อนุญาต; operational records สำหรับ screening, baseline, Program, Service 1, Goal Plan, Follow-up, Final; appointment coordination/read; personal medication/wellness; Hospital contact/content; factual per-Program readback.
- **Implemented but differs or narrower:** service request ไม่เท่ากับ enrollment/assignment; appointment acknowledgement ไม่เท่ากับ attendance; family read จำกัด appointment; personal exercise/medication/wellness ไม่ใช่ Program clinical service; report เป็น exact Program ไม่ใช่ cohort workbook.
- **Missing source behavior:** OSM assignment acceptance, confirmed service-delivery event, achieved-day observations/rate, structured overall follow-up outcome, explicit plan adjustment, structured follow-up obstacle, responsibility-area domain, coherent cohort/two-sheet export.
- **Requirement-open/deferred:** clinical definitions and units; caregiver resource/consent scope; service request downstream state; Hospital responsibility area; network aggregate privacy; HN-M08 export deferred/not authorized.
- **Technically implemented but UAT/security/external-setup blocked:** family real-device/real-data; medication/wellness manual UAT; content browser/mobile UAT; LINE provider/device; report export authorization/privacy/snapshot; Hospital operational verification.

ดังนั้นคำตอบต่อ “ระบบปัจจุบันเก็บ authoritative facts ได้ครบเพื่อสร้าง Dashboard และ Excel โดยไม่เดา clinical outcomes หรือข้าม authorization หรือไม่?” คือ **ยังไม่ได้**. หลักฐานระบุแหล่งจริงบางส่วน แต่ field สำคัญหลายรายการไม่มี source, ผูกกับ Program ไม่ได้, ไม่อยู่ใน reporting projection, ไม่มีสูตรที่รับรอง หรือยังไม่มี export permission. รายการ blocker และ next action ที่เล็กที่สุดจัดไว้ใน [Phase 18AB backlog](./PHASE_18AB_VERIFIED_GAP_BACKLOG.md); Phase 18A/18B ไม่อนุมัติ implementation.
