## 3. Hospital Network decision closure packages

### 3.1 HN-C1-D01 / HN-C1-D02 — Operation capabilities and directory fields

- **Current status:** HN-C1-D01 `OPEN_BLOCKER`; HN-C1-D02 `OPEN_BLOCKER`. Candidate names remain proposals.
- **Verified facts:** Existing local policy pattern is operation-specific. The structural resolver already checks current direct Parent OWNER scope, but its existence does not install a reporting capability. HN-A04 allows a future organizational directory to include direct children in `PENDING_VERIFICATION`, `ACTIVE`, or `SUSPENDED`; only ACTIVE children contribute to aggregates.
- **Recommended option — `RECOMMENDED_FOR_APPROVAL`:** Use separate server-side operations with candidate capabilities `network:directory:read`, `network:summary:read`, and `network:child-summary:read`. Keep child-summary as a separate capability because child-level output adds a disclosure dimension and can be denied independently. The minimal directory projection candidate is opaque Hospital ID, name, and status; add `hospitalCode` only if a documented use case establishes necessity.
- **Actor contract to approve:** ACTIVE User, current `Role.HOSPITAL`, direct ACTIVE OWNER membership at the exact ACTIVE Parent Hospital, and current server-resolved target scope. ADMIN-only, MEMBER-only, child-only OWNER, OSM/PATIENT without qualifying Parent OWNER authority, inactive/revoked actor or membership, and unrelated scope are denied. A multi-role ADMIN actor qualifies only through the same HOSPITAL + exact Parent OWNER conditions; ADMIN grants nothing by itself.
- **Scope denials:** No grandchildren, siblings, or unrelated Hospitals. A child locator is valid only while the database confirms it is an ACTIVE direct child of the authorized Parent; directory visibility does not grant child-summary permission.
- **Authorization decision points:** Authenticate from the current server session; map the server operation to its fixed capability (never accept a client-selected capability); treat Parent/Child IDs as locators; re-read current User status/Role, exact ACTIVE OWNER membership, and Parent status from the database; resolve current P/C/N from the authoritative direct-child relation; for child summary recheck that exact ACTIVE child belongs directly to the authorized Parent. Pass only this trusted scope to a future query, then revalidate authority/scope before result release. Revoke, demote, suspend, stale scope, invalid hierarchy, or failed authoritative read must deny/unavailable. These operations grant no Patient rows, clinical details, child workforce mutation, or export.
- **Alternatives:** Combine Network and child-summary under one permission; omit directory access; or revise capability names/scope. Do not reuse `report:program:read`, exact-Hospital reporting capabilities, governance-directory permissions, or Global selected-Hospital ADMIN access.
- **Trade-offs:** Separate operations make least privilege and deny behavior explicit, with a small local policy addition. More capability values require a clear server-side mapping. A directory-only grant reveals organizational status but no metrics; status must not imply child reporting authority.
- **Required authority:** Product Owner for operation and actor intent; Security for authorization boundary and deny cases; Privacy/Data Controller for directory field disclosure as required by governance; Architecture for policy integration.
- **Approval question:** “Approve the exact ACTIVE direct Parent OWNER actor contract and the three operation boundaries as separate capabilities, including a separately gated child-summary capability; and approve the directory allowlist as opaque ID/name/status, with `hospitalCode` excluded unless separately justified?”
- **Acceptance evidence:** Dated authority record naming the approving roles, exact capability names or replacements, actor/scope matrix, directory field allowlist, excluded operations, conditions/version, and review evidence. Engineering then supplies PostgreSQL synthetic allow/deny cases for every actor/state and direct-child boundary.
- **Implementation impact:** 19B.1 policy/scope resolution and focused PostgreSQL authorization tests; directory field decision also gates any directory consumer. No generic framework or capability assignment table is implied.
- **Final gate:** `BLOCKED` — no Network capability/policy acceptance or directory disclosure approval is recorded.

### 3.2 HN-C1-D03 / HN-C1-D04 — Historical reparenting and metric attribution

- **Current status:** HN-C1-D03 and HN-C1-D04 `OPEN_BLOCKER`; HN-A05 temporal principle is `OWNER_RECEIVED`. The requester selected Option A as engineering direction, recorded in HN-C1 direction record; this is not authority approval and does not prove which contributions can be identified.
- **Verified facts:** Current hierarchy stores current `parentHospitalId`; no authoritative effective-dated history is present. Current source association identifies a Hospital, but cannot prove that Hospital belonged to the current Parent at a past contribution time. `updatedAt`, Patient/relationship creation dates, Program timestamps, and Follow-up `recordedAt` do not establish parentage effective dates.
- **Recommended option — `RECOMMENDED_FOR_APPROVAL`:** Ratify Option A: withhold unverifiable historical contributions and fail closed wherever temporal authorization cannot be established. Do not infer a transfer date, assume a Hospital was never reparented, split records/episodes by guess, backfill history, or treat current ownership as historical permission.
- **How to identify an affected contribution:** A contribution is the metric-grain source row or distinct identity included because its source Hospital is in P/C/N, where authority to attribute that contribution to the current Network at the relevant time cannot be proven. Existing sources cannot reliably identify the transfer boundary or certify an unaffected historical population. If that uncertainty cannot be isolated to individual source contributions with approved provenance, withhold the entire metric cell for the affected Hospital/scope.
- **Required withholding boundary:**
  - **M01 Patient relationships/unique Patients and M02 current classifications:** CURRENT_SNAPSHOT values may contain old relationships and current profile-global classification. If an included Hospital may have been reparented and the affected population cannot be separated, withhold that metric for that Hospital. Withhold the full C metric when any eligible child contribution is unproven; withhold the full N metric when N would include such a contribution. A separately valid P cell is not automatically tainted by a child transfer, but may still require complementary suppression.
  - **M03 staff/OSM users and relationships:** current membership/OSM relationship state does not show historical Parent authority. Apply the same whole-cell/scope withholding if an included Hospital contribution is unprovable; M03 also remains blocked by D10.
  - **M04 Program episodes/participants:** do not split an episode spanning a reparent event. Withhold the whole affected episode attribution; if the episode/participant contribution cannot be isolated, withhold the full affected child, C, or N metric cell for that reporting interval.
  - **M05 Follow-up records/unique Patients:** `recordedAt` remains the accepted reporting time but is not proof of Parent authority. If historical hierarchy eligibility cannot be established for the linked relationship, withhold the full affected metric cell rather than return a partial total.
  - **P/C/N propagation:** child-only uncertain contribution withholds that child metric; any C aggregate containing it is withheld as a complete C cell; any N aggregate containing it is withheld as a complete N cell. Do not replace withheld values with zero or a partial total described as complete.
- **Parent ownership change/revocation:** The former Parent loses the child from current scope when reparenting is effective in current authoritative data; the new Parent receives no retrospective permission from the new pointer. Revocation/suspension blocks subsequent access after authoritative revalidation; prior disclosures cannot be recalled. No stale cached result may bridge the change.
- **Future source alternative:** An authoritative, complete, effective-dated hierarchy/provenance source could support attribution only after its owner certifies completeness, corrections, gaps, and the source event/time used for each metric. Authorities must approve metric-specific attribution rules, including mixed snapshots and Programs crossing a transfer. Unknown, conflicting, or uncovered periods remain withheld; any schema/history migration requires separate approval.
- **Alternatives:** Option B, an approved effective-dated source and per-metric attribution rule; or a prospective cutover with explicit handling of legacy snapshots. Neither has verified source support today.
- **Trade-offs:** Option A avoids retrospective over-disclosure but can make complete metrics unavailable for entire Hospital/scope/period until provenance exists. Option B may recover utility but needs authoritative source evidence and potentially approved persistence/migration; it cannot be inferred from current timestamps.
- **Required authority:** Product Owner, Security, Privacy, Data Controller, and relevant Hospital/metric Data Owner; Architecture/Data Owner must attest source completeness if proposing a temporal source.
- **Approval question:** “Approve Option A and accept that every M01–M05 cell whose complete eligible contribution cannot be proven is withheld at the whole affected Hospital/C/N metric scope, including mixed snapshots and Programs crossing reparenting; or identify and approve an authoritative effective-dated source plus metric-specific attribution and legacy cutover rules?”
- **Acceptance evidence:** Authority record with exact Option A withholding boundaries or selected alternative; source-owner evidence proving whether a contribution can be attributed, including unknown/gap/conflict handling; synthetic tests for old/new Parent, no-history and conflicting-history cases, mixed snapshot, Program crossing reparent, Follow-up before/after, and revocation. No real Patient data is needed or permitted for this evidence.
- **Implementation impact:** Blocks numeric Network query/projection in 19B.2 and Network Dashboard 19C.2 for affected metrics. No history table, migration, or backfill is authorized by this pack.
- **Final gate:** `BLOCKED` — no approved provenance/attribution policy and no source evidence that current data can separate affected contributions.

### 3.3 HN-C1-D05 / HN-C1-D06 / HN-C1-D07 — HN-M07 primary, complementary, and cross-request privacy

- **Current status:** HN-C1-D05, HN-C1-D06, HN-C1-D07 and HN-M07 `OPEN_BLOCKER`. No numeric threshold, suppression algorithm, permitted dimension set, query budget, release cadence, or acceptable risk is approved.
- **Verified facts:** Metric grains differ: M01/M02 include Patient identities and Hospital relationships; M03 includes Users and memberships/OSM-Hospital relationships; M04 includes Patient participants and Program episodes; M05 includes Patient identities and Follow-up records. The exact record and identity semantics remain those accepted in HN-C0.
- **Primary protected-unit candidates:** distinct Patient/User identity for unique counts; relationship IDs for relationship counts; Program IDs for episode counts; Follow-up IDs for record counts. Authorities must decide whether these are protected units, how rare cohorts are evaluated per metric, and what risk is acceptable. These candidates are not a threshold or policy.
- **Complementary arithmetic and set rules:** An equality such as `N.relationshipCount = P.relationshipCount + C.relationshipCount` is valid only when P/C partition the eligible source records without overlap and joins do not duplicate records. For distinct identities, recompute the union: `N.unique = |P_unique ∪ C_unique| = P.unique + C.unique - |P_unique ∩ C_unique|`. Do not assume the intersection is zero, and do not expose it or infer that internal computability permits publication. Suppression must consider arithmetic reconstruction for additive counts, set-overlap inference for unique counts, direct-child outputs, linked metrics, and repeated requests.
- **Cross-request threat set:** Overlapping time windows, different As-of instants, repeated refreshes, direct-child breakdowns, classification/related metric comparisons, reparenting, and suppressed-versus-unsuppressed response changes must be evaluated together. Rate limiting alone does not prevent differencing. Include already authorized exact-Hospital outputs as possible auxiliary values in the threat analysis; this does not modify their contracts.
- **Primary suppression behavior to decide:** For each metric/grain, define protected unit and risk treatment for small/rare cells. A true zero is available only when an authorized, complete source query proves zero. Suppressed, unauthorized, temporally unproven, no-eligible-contributor, and source-unavailable outcomes are non-numeric; do not emit zero or a partial value for any of them. Client wording should not expose whether a child/cohort exists or why a cell was withheld.
- **Complementary behavior to decide:** Define which related P/C/N, child, parent, classification, record-count, unique-count, or period outputs must be jointly withheld to block arithmetic reconstruction and unique-set overlap inference. A per-cell test alone is insufficient.
- **MVP option A — phased delivery with restricted disclosure dimensions and behavior:** Candidate first release, subject to explicit Product Owner approval of the delivery sequence, exposes only HN-M01 at the N scope and one server As-of per response; omit side-by-side P/C/child outputs, M02 classification splits, M03 until D10, and period-based M04/M05 from the first consumer. This is phased delivery, not reduction or cancellation of accepted scope: HN-A03's P, C, and N remain accepted Network aggregation scopes, and HN-A06's bounded aggregate breakdown of ACTIVE direct children remains in the backlog for a later slice, subject to its Privacy and History gates. If the unique-Patient and relationship-count pair is not approved together, authorities may permit one or neither; do not presume either is safe. This reduces output-vector and time-filter complexity while retaining useful top-level Network context. It does not itself make a cell safe: primary/complementary review must include existing exact-Hospital reports and repeated As-of refreshes. Deferring M04/M05 is a display-scope choice, not a change to their accepted definitions. Preserve all HN-M06 date semantics if M04/M05 are later exposed. If privacy control would reject or coarsen accepted date windows, obtain an explicit Product Owner decision amending HN-M06; do not change it silently.
- **MVP option B — richer reporting with formal disclosure control:** Permit P/C/N, child, classification, and period combinations only after a formally approved primary and complementary suppression design plus cross-request governance (for example, a reviewed release-history mechanism or another accepted control). This offers richer utility but needs more policy, implementation, test coverage, operational review, and possibly approved persisted release state/retention. No specific algorithm or migration is selected here.
- **Recommended option — `RECOMMENDED_FOR_APPROVAL`:** Submit Option A as a first-stage N-only delivery only if the Product Owner explicitly approves that phased sequence and confirms HN-A03 P/C/N scopes and the HN-A06 bounded ACTIVE direct-child breakdown remain accepted scope/backlog for later delivery after applicable gates. Release no real values until D05–D07 approve a testable policy for the reduced first-stage output vector, including comparisons against existing exact-Hospital values and repeated As-of refreshes. If period metrics are proposed later, require controls for repeated M06-compliant windows. If those controls cannot honor HN-M06, keep affected period metrics blocked and ask the Product Owner explicitly whether to amend the date contract. Option A is risk reduction, not an automatic privacy pass.
- **Required authority:** Product Owner, Security, Privacy, Data Controller, and relevant metric/Data Owners. Security/Privacy authorities set or accept disclosure risk; engineering does not select a threshold on their behalf.
- **Approval question:** “Will the Product Owner approve Option A as phased delivery—an initial HN-M01-at-N release—while retaining HN-A03's P, C, and N aggregation scopes as accepted requirements and HN-A06's bounded ACTIVE direct-child breakdown in the backlog for later delivery subject to Privacy and History gates, without treating either as cancelled or de-scoped? For the proposed N-only output vector, what protected unit and primary small/rare-cell rule are approved; which linked outputs must be suppressed jointly for additive-count arithmetic and distinct-identity overlap; and what cross-request behavior is permitted across HN-M06-compliant windows, As-of values, refreshes and reparenting? If the accepted time inputs must change, does the Product Owner explicitly approve an HN-M06 amendment?”
- **Acceptance evidence:** Authority record with metric/grain-specific protected units, risk/threshold or alternative policy, primary and complementary expected outcomes, permitted first-stage output dimensions, repeated-query behavior, treatment of zero/unavailable, effective version/conditions, and the exact HN-M06 decision; include an explicit Product Owner record accepting N-only as phased first-stage delivery while retaining HN-A03 P/C/N and HN-A06 bounded direct-child breakdown in accepted scope/backlog. Engineering supplies synthetic adversarial cases for arithmetic closure, union overlap, linked/child metrics, period differencing, suppression transitions, and existing exact-Hospital auxiliary outputs; no threshold is assumed before approval.
- **Implementation impact:** Blocks real aggregate release, suppression projection, and 19B.2/19B.3 privacy expectations. Stateful release governance is a possible data/migration requirement only if the selected policy needs it.
- **Final gate:** `BLOCKED` — HN-M07 has neither authority-approved policy nor tested expected outcomes.

### 3.4 HN-C1-D08 / HN-C1-D09 — Failure states, revocation, cache, audit and retention

- **Current status:** HN-C1-D08 and HN-C1-D09 `OPEN_BLOCKER`.
- **Verified facts:** ADR-0002 requires server authority and fail-closed denial. HN-C1 names internal outcome candidates but does not approve API/DTO mappings. Audit schema/service infrastructure exists; no Network reporting audit/retention policy is verified.
- **Recommended option — `RECOMMENDED_FOR_APPROVAL`:** Keep internal outcomes distinct: available factual zero, denied, temporal-unproven, privacy-withheld, no eligible contributor, and source-unavailable. Externally return a generic non-numeric unavailable response for withheld/unknown states. Default to private/no-store and no shared/public aggregate cache. Reauthorize every request and any future cache read. On scope change, revocation, incomplete authoritative read, or required audit failure, fail closed.
- **Data minimization:** Return only approved aggregate cells, scope labels and required freshness/time metadata. Do not return Patient/User identifiers, source rows, clinical values, raw predicates, suppressed counts or source error details. Audit/log metadata must never include Patient identifiers, clinical values, suppressed counts, raw source query or response body.
- **Minimum audit candidate:** event/correlation ID, actor reference, operation/capability, Parent and (when relevant and approved) target Child reference, event time, policy version, and coarse outcome category. Authority must decide whether to record allowed, denied, withheld, aborted, and suspicious requests; retention period, readers, purpose, deletion, and required behavior if audit persistence fails remain open.
- **Alternatives:** No Network read audit until a defined release policy requires one; or an expanded event contract. Broader audit fields increase retention/access burden. Omitting necessary audit can fail governance requirements. Neither alternative is accepted.
- **Trade-offs:** Generic client errors reduce existence/cardinality oracles but provide less diagnostic detail. Private/no-store and revalidation reduce stale/cross-actor exposure but do not retract already delivered data. Audit adds accountable operations and a sensitive metadata store that itself needs access/retention controls.
- **Required authority:** Product Owner, Security, Privacy, Data Controller/records governance, and Architecture/runtime owner.
- **Approval question:** “Approve the internal outcome distinctions and generic non-numeric client mapping, private/no-store with per-request reauthorization and no shared cache; and decide the minimal audit event classes/fields, readers, retention, and fail-closed behavior if a required audit write fails?”
- **Acceptance evidence:** Signed/dated role-based decision defining states and external mapping, revalidation boundary, cache policy, audit purpose/event catalog/allowlist/readers/retention/failure behavior. Engineering supplies tests that genuine zero differs internally from withheld/unavailable, client responses do not expose existence or counts, audit has no prohibited fields, and revoked scope cannot access a later request/cache.
- **Implementation impact:** 19B.1 request boundary, 19B.2 projection/error handling, 19B.3 PostgreSQL regression tests, and possibly audit schema/migration only if approved design requires persistence.
- **Final gate:** `BLOCKED` for Network result serving — error mapping, revocation race, and audit/retention contracts are not approved.

### 3.5 HN-C1-D10 — HN-M03 eligibility and truthful labels

- **Current status:** HN-C1-D10 and exact HN-M03 eligibility `OPEN_BLOCKER`. Predicates below are engineering candidates, not accepted reporting semantics.
- **Verified facts:** `HospitalMembership` stores type, status, optional profession and User relation; `OsmHospitalRelationship` has its own status and User relation. User status and roles are separate persisted facts. OWNER/MEMBER is not evidence that a person is clinical staff.
- **Recommended predicates — `RECOMMENDED_FOR_APPROVAL`:**
  - Staff candidate: ACTIVE User, `Role.HOSPITAL`, ACTIVE HospitalMembership of type OWNER or MEMBER, and exact eligible Hospital scope.
  - OSM candidate: ACTIVE User, `Role.OSM`, ACTIVE OsmHospitalRelationship, and exact eligible Hospital scope.
  - Count distinct User IDs separately from eligible relationship IDs. Do not add Staff and OSM unique counts into a general unique workforce metric. A multi-role User may appear once in each separate metric.
- **Recommended labels:** Replace “Staff” with “Hospital user accounts” or “Hospital members” for distinct User count; label relationship count “Active Hospital memberships.” For OSM, use “OSM user accounts” and “Active OSM–Hospital relationships.” Do not use “clinical staff” unless the Product/clinical domain explicitly defines the required profession population and its source predicate.
- **Assessment:** These candidates are suitable for approval only as account/membership metrics. If product intent is clinical workforce, require a narrower profession-based definition; current optional profession data and OWNER/MEMBER membership do not support claiming a clinical workforce count.
- **Inconsistent states and required synthetic PostgreSQL cases:** active relationship with missing required role; active relationship with PROVISIONED, INVITED, or SUSPENDED User; active User/role with inactive or revoked relationship; OWNER/MEMBER membership with no `Role.HOSPITAL`; OSM relationship with no `Role.OSM`; inactive Parent/child; membership/relationship outside exact eligible Hospital; multi-role User with both Staff and OSM relationships; same User in multiple eligible Hospitals; and status/role changes concurrent with aggregation. Candidate predicates exclude invalid combinations; do not auto-repair source records as part of reporting.

### 3.6 HN-C1-D11 — Read consistency, revocation and release boundary

- **Current status:** HN-C1-D11 `OPEN_BLOCKER`; no Network isolation/revocation strategy is selected.
- **Verified facts:** Current exact-Hospital reporting uses Prisma `RepeatableRead` for a multi-query read and revalidates access after projection assembly for the page path. PostgreSQL and Prisma transactions are available. The Network resolver and aggregate query are not yet one transactionally bound operation.
- **Recommended option — `RECOMMENDED_FOR_APPROVAL`:** Evaluate a bounded `RepeatableRead` transaction as the initial Network design: perform fresh actor/Parent/direct-child scope resolution and all aggregate queries on the same transaction client; capture one server-authoritative As-of instant for accepted timestamp predicates; build a minimal DTO; then perform a fresh final authorization and scope check before release, comparing the authorized Parent/child set and current statuses. Abort if state is missing, contradictory, or changed. Reauthorize each later request; use no shared/public aggregate cache.
- **What this guarantees:** When every read uses the same PostgreSQL transaction client, RepeatableRead provides a coherent transaction snapshot for those reads. It can prevent separate metric queries in that transaction from silently mixing committed database snapshots. See the [PostgreSQL transaction isolation documentation](https://www.postgresql.org/docs/current/transaction-iso.html) and [Prisma ORM 6 transaction documentation](https://www.prisma.io/docs/orm/v6/prisma-client/queries/transactions).
- **What this does not guarantee:** The As-of instant does not itself create a database snapshot or reconstruct mutable states. RepeatableRead does not see commits made after its snapshot, does not prove historical hierarchy, and does not make authorization atomic with response delivery. A final check narrows the revocation window but a revocation after that check can race with response transmission.
- **ABA limitation:** Comparing the final current scope/status with the initial scope does not detect an intermediate change that returns to the same values, such as reparent-away-then-back or suspend-then-restore. No Network hierarchy version/event history has been verified. If policy requires detecting every intermediate transition, that need must be demonstrated and approved before choosing a version or locking design.
- **Race handling recommendation:**
  - Use transaction isolation for scope/source consistency across the read set.
  - Use an optimistic final re-read of User status/role, exact ACTIVE OWNER membership, Parent status, direct-child relationship/status and scope identity; cancel release on mismatch.
  - Treat that current-state comparison as optimistic validation only; it is not proof that no intermediate ABA transition occurred.
  - Retry only a bounded, explicitly classified transaction failure when the read can be safely restarted under a fresh authorization check. Otherwise return safe unavailable.
  - Do not add locks, schema version counters, or new version infrastructure unless a demonstrated race or an authority-required stronger guarantee needs them. SERIALIZABLE alone does not make HTTP delivery atomic.
  - Explicitly accept or reject the residual in-flight race: a response authorized at the final check may still be transmitted just after revocation commits. Revocation always blocks subsequent requests; previously delivered data cannot be recalled.
- **Alternatives:** A single bounded database statement may reduce cross-statement inconsistency but does not eliminate authorization/revocation or disclosure risks. Stronger locking/version coordination may narrow selected races but adds contention and write-path coordination; test a concrete race before choosing it.
- **Required authority:** Architecture/database and Security authorities, with Product Owner deciding acceptable revocation behavior and Data Owner confirming source-time semantics.
- **Approval question:** “Approve one RepeatableRead snapshot for server-resolved scope and aggregate reads, a fresh final authority/scope check with abort-on-change, no shared cache, and the stated residual in-flight delivery race; or specify the stronger revocation guarantee and concrete race evidence that requires additional coordination?”
- **Acceptance evidence:** Written isolation/snapshot boundary and residual-risk decision; PostgreSQL concurrency tests for membership revoke/demotion, User suspension, Parent/child suspension/reparent, source updates and scope-set mismatch; evidence that all scoped reads use the transaction client and that failed/retried requests reauthorize. Do not claim As-of alone is snapshot consistency.
- **Implementation impact:** Gates transaction boundary for 19B.1/19B.2 and concurrency expectations in 19B.3. No lock/version migration is assumed.
- **Final gate:** `BLOCKED` — no authority-approved consistency guarantee or race evidence exists for a Network read.
