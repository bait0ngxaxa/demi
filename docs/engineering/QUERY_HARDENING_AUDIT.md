## Quarantine decision (three exceptions)

The three queries run after persisted ADMIN validation in the existing SERIALIZABLE transaction. They preserve all unreconciled predicates and merge results by claim time. The only production caller found is `reconcilePlatformAdminBreakGlassPassword`, which filters the complete result to one ADMIN's unique `BREAK_GLASS_CLI` reset. Other uses are integration tests; no production queue UI consumes this listing. An item can remain quarantined indefinitely if provider outcome cannot be confirmed; neither expiry nor an assumption of low volume proves a bound. No item is silently dropped and no lifecycle/audit transition changes.

Remaining risk: global recovery rows and Person display fields are materialized inside an ADMIN-authorized transaction, even for that single-ADMIN lookup. Follow-up: use a narrowly scoped break-glass lookup with the same uniqueness/safety checks; introduce per-storage keyset iteration for a future complete operational inventory, including stable merge ordering, more-than-one-batch tests and reconciliation during traversal. All three exceptions remain explicit `FOLLOW-UP` entries. This review does not claim bounded memory or operational queue-volume evidence for them.

## Limits and guard

The import still scans O(registry size), and its required result can grow with the number of actual name matches. Batching bounds each read and avoids retaining unrelated Hospitals; it does not promise bounded total latency or a constant-sized response. The existing transaction timeout is unchanged. The CLI inventory is live: new/replaced operations behind its cursor need another invocation; resolved items ahead can disappear. It is not a snapshot or proof of queue completion. A failed read propagates and the CLI exits unsuccessfully; no success state is persisted by listing.

## Production latency follow-up — 2026-11-07 review

The import memory fix is not a latency closure. Before production, the deployment owner must supply the expected registry size, maximum supported CSV workload and acceptable preview/apply latency; none is established by this audit. Measure the real `evaluateRegistrationRows` preview and apply paths against that registry size (including normalized matches and file duplicates), with the deployed PostgreSQL/network topology. Record dataset size, submitted row count, match density, batch/query count, transaction duration, p50/p95 wall latency, serialization retries and timeout/failure rate, including concurrent imports/writes. Retain normalization, confirmation and race-condition assertions while measuring.

Disposition: **measurement pending; no production-scale latency result claimed**. The 503-Hospital correctness fixture is not a production benchmark. Investigate a normalized lookup/index or another targeted alternative only if measurements demonstrate a problem; do not replace complete duplicate detection with a sample or silently raise transaction deadlines.
