# Rich Menu exact PNG references

`assets-linux.sha256.json` records SHA-256 for all 18 committed Windows-generated PNGs and all 18 native Linux renderings. It is a test-only golden, not a generator input or deployed asset. The test checks the exact catalog filename set, committed asset hashes and exact generated output: Linux against its golden, other platforms against committed bytes. No pixel tolerance is applied; overflow, Thai label, font checksum, dimensions, size and hitbox assertions remain active.

Provenance: reproduced the sole unit failure from [run 42357321564](https://github.com/bait0ngxaxa/demi/actions/runs/42357321564) at CI commit `07612532b4cf7d35927b79d0aa46b28c76e796ca` in a clean Linux workspace using `npm ci`, Node 24.22.1 and the bundled checksum-pinned Noto Sans Thai 2.002 font. Windows passes the original byte comparison. Linux repeated rendering of every image was byte-identical but differed from the Windows PNGs; even decoded RGBA differs (UNLINKED: 46,546 channel values). This rules out compression-only variation and nondeterministic rendering. Sharp 0.35.3 / libvips 8.18.3 uses native platform packages: Linux Pango 1.58.0 / librsvg 2.62.90 versus Windows Pango 1.57.1 / librsvg 2.62.3. Contact-sheet inspection of all 18 paired images found matching content/layout; this does not replace device UAT.

When intentionally changing assets/renderer/native dependencies, regenerate in clean Windows and Linux environments from the same source and lockfile, render each variant twice to confirm determinism, inspect paired output (including full-resolution Thai text), and review both committed and Linux hashes. Compute `createHash("sha256").update(buffer).digest("hex")` directly from each PNG. Do not update goldens simply because CI fails. The production asset generator and its `--check` behavior remain unchanged; its byte check still targets the committed Windows rendering. No production PNG is changed by this CI portability fix.
